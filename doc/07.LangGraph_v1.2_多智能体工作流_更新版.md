# 0. 2026 更新重点

原 PDF 的主线没有过时，但若直接照旧代码学习，会形成几个错误或不完整的理解。

| 原 PDF 的说法 / 写法 | 2026 更准确的理解 |
|---|---|
| Streaming 主要讲 `updates / messages / values / custom` | Raw stream mode 现在包括 `values / updates / messages / custom / checkpoints / tasks / debug`；新应用优先了解 `stream_events(version="v3")` typed projections |
| `values` 是“默认一次拿到所有 chunk” | 更准确：`values` 在每个 step 后输出完整 State；`updates` 只输出该 step 的局部更新 |
| Checkpointer 就是消息持久化 | Checkpointer 保存的是 **thread 的 Graph State checkpoints**，消息只是 State 的一种字段 |
| Store 和 Checkpointer 都可以看成“记忆” | Checkpointer = thread-scoped short-term state；Store = cross-thread application data / long-term memory |
| Interrupt 不能等太久，否则无法恢复 | 当前 LangGraph interrupt 会持久化状态，并可以长期等待；生产环境必须使用持久化 checkpointer |
| `interrupt()` 后从中断那一行继续执行 | 恢复时，包含 `interrupt()` 的 **Node 会从头重新执行**；因此 interrupt 前不能放不可重复的副作用 |
| Time Travel = 从某个 Node 回退重跑 | 当前更准确：基于历史 **checkpoint** 做 Replay 或 Fork；Replay 重新执行之后的 Node，Fork 在修改 State 后创建新分支 |
| `update_state()` 会修改过去的历史 | 不会。它创建新的 checkpoint / branch，原执行历史保留 |
| 多智能体调试主要靠 `custom` | `custom` 仍很实用；另外当前 event streaming 可直接观察 messages、state、subgraphs、interrupts 与 final output |

LangGraph 1.2 的运行时能力可以浓缩成：

```text
Graph Execution
   ↓
Streaming / Events
   ↓
Checkpoints
   ↓
Pause / Resume
   ↓
Inspect History
   ↓
Replay / Fork
```

这正是 07 与 06 的区别：

```text
06. Multi-Agent

```

# 一、Streaming：先看见 Workflow 正在做什么

原课程把 Streaming 放在第一节是对的，因为一个复杂 Graph 如果只能在最后返回结果，几乎无法理解中间发生了什么。

当前 LangGraph 有两层常用方式：

```text
Low-level stream modes
stream() / astream()
  ↓
values / updates / messages / custom / checkpoints / tasks / debug

Higher-level event streaming
stream_events(..., version="v3")
  ↓
typed projections:
messages / values / subgraphs / interrupts / output / extensions
```

## 1.1 Raw stream mode：`updates`

`updates` 最适合刚开始调试 Graph：你可以直接看到每个 Node 修改了哪些 State。

```python
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END


class State(TypedDict):
    query: str
    route: str
    result: str


def router(state: State):
    return {"route": "demo_worker"}


def worker(state: State):
    return {"result": f"handled:{state['query']}"}


graph = (
    StateGraph(State)
    .add_node("router", router)
    .add_node("demo_worker", worker)
    .add_edge(START, "router")
    .add_edge("router", "demo_worker")
    .add_edge("demo_worker", END)
    .compile()
)

for part in graph.stream(
    {"query": "hello", "route": "", "result": ""},
    stream_mode="updates",
    version="v2",
):
    if part["type"] == "updates":
        print(part["data"])
```

你会看到类似：

```text
router      -> {route: demo_worker}
demo_worker -> {result: handled:hello}
```

### `updates` 的价值

它回答的是：

> **“哪个 Node 刚刚改了什么？”**

对于 Router / Supervisor / Worker 调试，这通常比最后答案更重要。

## 1.2 Raw stream mode：`values`

`values` 则是在每一个 step 后返回完整 State。

```python
for part in graph.stream(
    {"query": "hello", "route": "", "result": ""},
    stream_mode="values",
    version="v2",
):
    if part["type"] == "values":
        print(part["data"])
```

区别：

```text
updates
= 只看增量

values
= 每一步后的完整 State snapshot
```

学习 Graph 时：

- 查路由错误：优先 `updates`
- 查完整 State 演进：用 `values`

## 1.3 `messages`：模型 Token / Message

如果某个 Node 内调用 Chat Model，可以使用 `messages`：

```python
for part in graph.stream(
    input_state,
    stream_mode="messages",
    version="v2",
):
    if part["type"] == "messages":
        message_chunk, metadata = part["data"]
        print(message_chunk.content, end="", flush=True)
```

`metadata` 可以告诉你这个 token 来自哪个 graph node。

在 06 的 Multi-Agent 中，这一点特别重要：

```text
Supervisor Model
Worker Model A
Worker Model B
```

可能都在生成消息。如果不看 metadata，很容易不知道输出属于谁。

## 1.4 `custom`：业务级调试 / 进度事件

原 PDF 对 `custom` 的定位仍然非常有价值。

```python
from langgraph.config import get_stream_writer


def retrieve_worker(state: State):
    writer = get_stream_writer()
    writer({"stage": "retrieval", "status": "started"})

    # ... do work ...

    writer({"stage": "retrieval", "status": "finished"})
    return {"result": "done"}
```

消费：

```python
for part in graph.stream(
    input_state,
    stream_mode="custom",
    version="v2",
):
    if part["type"] == "custom":
        print(part["data"])
```

适合：

- UI 进度条
- Worker 当前阶段
- Retriever 找到多少文档
- Supervisor 正在委派哪个专家
- 调试长任务

## 1.5 其他 raw stream modes

当前还包括：

| mode | 用途 |
|---|---|
| `checkpoints` | Checkpoint 事件，需要 checkpointer |
| `tasks` | Node / task 开始、结束、结果、错误 |
| `debug` | 最完整的 runtime debug 信息 |

教学阶段不需要每种都写复杂案例，但必须知道它们存在。

# 二、Event Streaming v3：新应用更推荐的消费方式

LangGraph 1.2 推荐新应用了解：

```python
graph.stream_events(..., version="v3")
```

它不是简单再加一个 `stream_mode`，而是把同一条运行时事件流投影成不同的 typed views。

## 2.1 最小用法

```python
stream = graph.stream_events(input_state, version="v3")

for snapshot in stream.values:
    print(snapshot)

final_state = stream.output
```

如果有 LLM：

```python
stream = graph.stream_events(input_state, version="v3")

for message in stream.messages:
    for token in message.text:
        print(token, end="", flush=True)

final_state = stream.output
```

## 2.2 为什么更适合应用层？

因为应用不必自己判断：

```python
if chunk["type"] == ...
```

而可以分别消费：

```text
stream.messages
stream.values
stream.subgraphs
stream.interrupts
stream.output
```

概念上：

```text
One Runtime Event Flow
      ↓
Typed Projections
 ├─ Messages
 ├─ State Values
 ├─ Subgraphs
 ├─ Interrupts
 └─ Final Output
```

## 2.3 Multi-Agent 特别有用：`stream.subgraphs`

当 Worker Agent / 子图嵌在父图里时：

```python
stream = graph.stream_events(input_state, version="v3")

for subgraph in stream.subgraphs:
    print(subgraph.graph_name, subgraph.path)
```

这样可以直接看到：

```text
Parent workflow
  ↓
record_worker subgraph
  ↓
doctor_worker subgraph
```

而不是自己解析复杂 namespace。

### 07 推荐学习原则

```text
想理解底层 Graph runtime
→ 先学 stream_mode

想写真实应用消费代码
→ 再学 event streaming v3
```

# 三、Persistence：Graph 不是执行完就消失

原 PDF 第二节叫“大模型消息持久化”，今天建议改成更准确的：

> **Graph Persistence / State Persistence**

因为 Checkpointer 保存的是 Graph State snapshot，而不仅是 Chat Messages。

## 3.1 Checkpointer 做什么？

```text
Graph Step 1
 ↓
Checkpoint
 ↓
Graph Step 2
 ↓
Checkpoint
 ↓
Graph Step 3
 ↓
Checkpoint
```

每个 checkpoint 都与某个 thread 关联。

它可以支撑：

- 多轮会话
- 中断 / 恢复
- 故障恢复
- 状态检查
- Time Travel

## 3.2 最小 InMemorySaver

```python
from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)

config = {
    "configurable": {
        "thread_id": "demo-thread-1"
    }
}

result = graph.invoke(initial_state, config=config)
```

这里最重要的不是 `InMemorySaver` 本身，而是：

```text
thread_id
= 当前 thread 的持久化游标 / namespace key
```

同一个 `thread_id`：

```text
继续同一条执行历史
```

新的 `thread_id`：

```text
创建新的独立 thread
```

## 3.3 `get_state()`：查看当前 checkpoint

```python
snapshot = graph.get_state(config)

print(snapshot.values)
print(snapshot.next)
print(snapshot.config)
```

常见关注项：

- `values`：当前 State
- `next`：下一步要执行的 Node / task
- `config`：包含 checkpoint 信息的配置

如果 `next` 为空，通常表示这个执行分支当前已经完成。

## 3.4 `get_state_history()`：查看完整 checkpoint 历史

```python
history = list(graph.get_state_history(config))

for snapshot in history:
    print(
        snapshot.next,
        snapshot.config["configurable"].get("checkpoint_id"),
    )
```

历史通常按较新的 checkpoint 在前排列，因此不要默认 `history[0]` 一定是“最早一步”。

这条历史是 Time Travel 的基础。

# 四、Checkpointer vs Store：短期状态和长期记忆不是一回事

这是原课程提到但需要强化的边界。

| | Checkpointer | Store |
|---|---|---|
| 保存 | Graph State snapshots | 应用自定义数据 |
| Scope | 一个 thread | 可跨 threads |
| 典型用途 | 对话连续性、HITL、Time Travel、恢复 | 用户偏好、事实、共享知识 |
| 访问方式 | `thread_id` | namespace + key / search |

## 4.1 Checkpointer = thread-scoped short-term state

例如：

```text
Thread A
messages
selected_worker
approval_state
current_task
```

它们都可以跟随 Graph State 一起保存。

## 4.2 Store = cross-thread application memory

例如：

```text
user_123
 ├─ preference: "concise answers"
 └─ favorite_topic: "cloud"
```

不同 thread 都可能读取同一个用户数据。

Local-first 可以用：

```python
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()
```

然后：

```python
graph = builder.compile(
    checkpointer=InMemorySaver(),
    store=store,
)
```

### 本章不要过度扩展 Long-term Memory

07 的核心仍然是 workflow runtime。Store 在这里掌握边界即可，不需要再造一个完整 memory product。

# 五、InMemorySaver 不是生产级持久化

学习时使用：

```python
InMemorySaver()
```

非常方便，但它只存在于当前进程内。

```text
Process exits
→ checkpoints disappear
```

本地开发如果想跨进程保存，可以考虑 SQLite checkpointer；生产环境常见 Postgres / Redis 等持久化实现。

本章 E2E：

```text
InMemorySaver
= 核心 PASS 足够
```

不要因为没有外部数据库阻塞课程。

但要建立工程意识：

> **HITL 等待数小时 / 数天的能力，真正依赖持久化 Checkpointer，而不是 RAM。**

# 六、Human-in-the-Loop：Graph 可以真正停下来等人

原 PDF 第三节的核心思路仍然正确：

```text
Graph
 ↓
Risk / Review Point
 ↓
interrupt()
 ↓
Persist State
 ↓
Wait for Human
 ↓
Command(resume=...)
 ↓
Continue
```

## 6.1 Interrupt 的三个硬条件

要使用 dynamic interrupt：

1. Graph 必须有 checkpointer。
2. 调用时必须提供 `thread_id`。
3. Node 内调用 `interrupt(payload)`。

```python
from typing_extensions import TypedDict
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command


class State(TypedDict):
    request: str
    approved: bool
    result: str


def approval_node(state: State):
    approved = interrupt({
        "type": "approval",
        "question": f"Approve action: {state['request']}?",
    })
    return {"approved": bool(approved)}


def execute_node(state: State):
    if not state["approved"]:
        return {"result": "rejected"}
    return {"result": "SIMULATED_ACTION_EXECUTED"}


builder = StateGraph(State)
builder.add_node("approval", approval_node)
builder.add_node("execute", execute_node)
builder.add_edge(START, "approval")
builder.add_edge("approval", "execute")
builder.add_edge("execute", END)

graph = builder.compile(checkpointer=InMemorySaver())
```

## 6.2 第一次运行：暂停

```python
config = {
    "configurable": {
        "thread_id": "approval-demo-1"
    }
}

result = graph.invoke(
    {
        "request": "delete synthetic resource",
        "approved": False,
        "result": "",
    },
    config=config,
)

print(result["__interrupt__"])
```

默认 `invoke()` 仍然可以从 `__interrupt__` 读取 interrupt 信息。

## 6.3 Resume

```python
final = graph.invoke(
    Command(resume=True),
    config=config,
)

print(final["result"])
```

必须使用同一个 `thread_id`。

```text
interrupt thread_id = X
resume thread_id    = X
```

否则是另一条 thread，不是恢复原任务。

# 七、2026 很重要的修正：Interrupt 可以长期等待

原 PDF 写：

> interrupt 时间不能过长，否则无法恢复。

当前 LangGraph 文档并不是这样定义的。

LangGraph interrupt 的设计就是：

> **保存当前状态，然后等待外部输入，直到你再次 resume。**

真正决定“能不能等几小时 / 几天”的是：

- 你是否使用持久化 checkpointer
- Checkpoint retention policy
- 数据库是否还存在
- 应用自己的业务超时
- 部署环境是否保留 thread / checkpoint

因此：

```text
InMemorySaver + 程序一直活着
→ 可以继续

InMemorySaver + 进程重启
→ 状态丢失

Persistent Saver + 进程重启
→ 可以恢复历史 thread
```

# 八、Interrupt 的隐藏坑：Resume 时 Node 会从头执行

这是做可靠 Agent 必须知道的细节。

例如：

```python
def approval_node(state):
    charge_credit_card()       # ❌ 副作用
    approved = interrupt("approve?")
    ...
```

第一次调用：

```text
charge_credit_card()
interrupt()
→ pause
```

Resume 后 Node 会重新开始：

```text
charge_credit_card()   ← 又执行一次
interrupt()            ← resume value 从这里返回
```

于是可能产生双重副作用。

## 正确做法

```text
Prepare / Validate
 ↓
interrupt approval
 ↓
Approved?
 ↓
Side-effect Node
```

也就是说：

> **真正不可重复的副作用放到 interrupt 之后的独立 Node。**

或者确保副作用具有 idempotency。

这个思想与 03 的 HITL / idempotency 完全一致。

# 九、用 Event Streaming 驱动 HITL

对于新的交互式应用，当前更推荐让 event stream 同时承担：

- token streaming
- state snapshots
- interrupt detection
- final output

```python
from langgraph.types import Command

stream_input = initial_state

while True:
    stream = graph.stream_events(
        stream_input,
        config=config,
        version="v3",
    )

    for message in stream.messages:
        for token in message.text:
            print(token, end="", flush=True)

    if not stream.interrupted:
        final_state = stream.output
        break

    interrupt_info = stream.interrupts[0].value
    print("Need human input:", interrupt_info)

    # 教学版：模拟人工选择
    user_response = True
    stream_input = Command(resume=user_response)
```

这比应用自己同时维护：

```text
LLM token stream
+ state stream
+ __interrupt__ detection
+ final result
```

更容易组织。

# 十、多个 Interrupt：多分支审批

复杂 Multi-Agent 可能出现：

```text
Supervisor
 ├─ Worker A → interrupt
 └─ Worker B → interrupt
```

如果多个并行分支同时中断，恢复时需要把每一个 interrupt ID 与对应的 resume value 匹配。

07 不要求把这个做成复杂 UI，但需要知道：

```text
One interrupt
→ Command(resume=value)

Multiple interrupts
→ map interrupt IDs to resume values
```

否则并行审批很容易把人的回答应用到错误任务。

# 十一、Time Travel：不是“魔法回滚”，而是 checkpoint replay / fork

原 PDF 最后讲 Time Travel，这是 LangGraph 很有价值的一层。

当前更推荐明确分成两个动作：

```text
Replay
= 从历史 checkpoint 重新执行后续步骤

Fork
= 从历史 checkpoint 修改 State，创建新的执行分支
```

## 11.1 先运行一个最小 Graph

为了把 Time Travel 与 LLM 随机性分开，先用 deterministic 示例。

```python
from typing_extensions import TypedDict, NotRequired
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import StateGraph, START, END


class State(TypedDict):
    topic: NotRequired[str]
    output: NotRequired[str]


def choose_topic(state: State):
    return {"topic": "cloud"}


def build_output(state: State):
    return {"output": f"topic={state['topic']}"}


graph = (
    StateGraph(State)
    .add_node("choose_topic", choose_topic)
    .add_node("build_output", build_output)
    .add_edge(START, "choose_topic")
    .add_edge("choose_topic", "build_output")
    .add_edge("build_output", END)
    .compile(checkpointer=InMemorySaver())
)
```

运行：

```python
config = {
    "configurable": {
        "thread_id": "time-travel-demo"
    }
}

result = graph.invoke({}, config=config)
print(result)
```

## 11.2 查看历史

```python
history = list(graph.get_state_history(config))

for snapshot in history:
    print(
        snapshot.next,
        snapshot.values,
        snapshot.config["configurable"].get("checkpoint_id"),
    )
```

找到：

```text
next == ("build_output",)
```

意味着：

```text
choose_topic 已完成
build_output 尚未执行
```

# 十二、Replay：从过去重新执行

```python
before_output = next(
    s for s in history
    if s.next == ("build_output",)
)

replayed = graph.invoke(
    None,
    before_output.config,
)
```

这里：

```text
choose_topic
→ 不重新执行

build_output
→ 重新执行
```

非常重要：Replay 不只是“读历史结果”。

之后的 Node 会真正重新执行，因此：

- LLM 可能给出不同回答
- API 会再次调用
- Tool 会再次执行
- Interrupt 会再次触发

所以 Time Travel 与副作用治理必须一起考虑。

# 十三、Fork：改 State 后走一条新路线

如果想说：

> “保留前面执行结果，但把 topic 改成 ai，然后从这里继续。”

使用：

```python
fork_config = graph.update_state(
    before_output.config,
    values={"topic": "ai"},
)

fork_result = graph.invoke(
    None,
    fork_config,
)

print(fork_result["output"])
# topic=ai
```

## 13.1 `update_state()` 不是覆盖旧历史

这是最关键的理解：

```text
Original branch
choose_topic=cloud
 ↓
build_output

Fork branch
choose_topic=cloud
 ↓
update_state(topic=ai)
 ↓
build_output
```

原来的执行链仍然存在。

因此 Time Travel 更接近：

```text
Git branch
```

而不是：

```text
Undo 删除历史
```

## 13.2 `as_node`

多数时候 LangGraph 可以根据 checkpoint 历史推断这次 State Update 应视为哪个 Node 产生。

复杂并行图里若无法推断，可以显式指定：

```python
fork_config = graph.update_state(
    before_output.config,
    values={"topic": "ai"},
    as_node="choose_topic",
)
```

这样执行会从 `choose_topic` 的 successor 继续。

---

# 十四、Time Travel + Interrupt

如果历史路径里包含：

```python
interrupt(...)
```

Replay/Fork 后重新经过这个 Node 时，Interrupt 也会再次触发。

例如：

```text
Checkpoint
 ↓
approval_node (interrupt)
 ↓
execute
```

Time Travel 回到 approval 前：

```text
approval_node
→ 再次 interrupt
→ 等新的 Command(resume=...)
```

这实际上非常有用：

> 可以针对历史流程，重新做一次审批并探索另一种决策路径。

---

# 十五、把这些能力加回 06 的 Multi-Agent Workflow

07 不是让你重新实现一套 Multi-Agent。

应该直接把运行时能力叠加到 06 的 Router / Supervisor 结构上。

## 15.1 Router Workflow + Streaming

```text
User Query
 ↓
Router                     ← stream updates
 ↓
Selected Worker            ← stream custom / messages
 ↓
Aggregate                  ← stream updates
 ↓
Final Answer
```

你可以清楚看到：

```text
route=record
record_worker started
record_worker finished
aggregate updated final_answer
```

## 15.2 Multi-Agent + Checkpointer

State 可以保存：

```text
messages
route
selected_worker
worker_result
approval_status
final_answer
```

同一个 `thread_id`：

```text
下一轮可以恢复相同 thread 的状态
```

但不要把所有 Worker 的内部消息都无脑放进父图 State。

继续遵守 06 的 Context Isolation。

## 15.3 Multi-Agent + HITL

例如在 Supervisor 要执行一个模拟高风险 Worker 前：

```text
Supervisor
 ↓
Proposed Action
 ↓
Approval Node
 ↓ interrupt
Human
 ├─ approve → risky_worker
 └─ reject  → safe fallback / END
```

这里推荐：

```text
Approval Node
和
Side-effect Worker
```

分开。

这样 Resume 时 Approval Node 重跑不会重复真实副作用。

## 15.4 Multi-Agent + Time Travel

例如：

```text
Router chose Record Worker
 ↓
Record Worker
 ↓
Aggregate
```

你发现 Router 选错了。

可以从 Router 后的 checkpoint Fork：

```text
update_state(route="doctor")
 ↓
从新的 route 分支继续
```

这就是 Time Travel 对多 Agent 调试最直观的价值。

# 十六、Subgraph 与 Multi-Agent Streaming

06 中 Worker 可能是：

- 一个普通 Node
- 一个 `create_agent()` compiled graph
- 一个 LangGraph Subgraph

如果要在 parent graph 的 raw stream 中看到 subgraph 内部事件：

```python
for part in graph.stream(
    input_state,
    stream_mode="updates",
    subgraphs=True,
    version="v2",
):
    print(part["ns"], part["data"])
```

`ns` 可以告诉你事件来自父图还是某个子图。

在 Event Streaming v3 中：

```python
stream = graph.stream_events(input_state, version="v3")

for subgraph in stream.subgraphs:
    print(subgraph.graph_name, subgraph.path)
```

对于多智能体系统，这比把所有调试信息写进同一个字符串日志更清晰。

# 十七、可靠性边界：Checkpoint 不是万能事务

有了 Checkpoint，不代表所有外部动作自动 exactly-once。

例如：

```text
Node A
 ↓
调用第三方付款 API
 ↓
进程在 checkpoint 前崩溃
```

恢复时可能再次调用付款 API。

因此真正可靠的 workflow 仍然需要：

- Idempotency key
- 幂等 Tool / API
- 明确 Side-effect Boundary
- Retry Policy
- Compensation / reconciliation

LangGraph 提供：

```text
保存执行状态
恢复控制流
```

但外部系统的事务语义仍然由你的系统设计负责。

```text
Stage J  06 Multi-Agent + Streaming / Persistence

Stage L  Final Runtime Verification
```

## 最关键的 E2E 1：Persistence

```text
Input
 ↓
Graph
 ↓
Checkpoint 1
 ↓
Checkpoint 2
 ↓
get_state / get_state_history
 ↓
PASS
```

## 最关键的 E2E 2：HITL

```text
Input
 ↓
Graph
 ↓
interrupt
 ↓
Persist
 ↓
Human approve/reject
 ↓
Command(resume)
 ↓
Continue
```

## 最关键的 E2E 3：Time Travel

```text
Historical Checkpoint
 ├─ Replay → same state, re-run future nodes
 └─ Fork   → modified state, new future branch
```

# 二十一、章节总结

原课程 07 最重要的思想仍然成立：

> 一个多智能体系统真正能落地，不只是因为它会“调用多个 Agent”，还因为它能被观察、保存、暂停、恢复、检查和重新执行。

2026 版完整认知链路：

```text
Multi-Agent Graph
   ↓
Streaming / Event Streaming
   ↓
Checkpointer + thread_id
   ↓
State History
   ↓
Human Interrupt / Resume
   ↓
Replay / Fork
   ↓
Reliable Runtime Design
```

与整个课程的关系：

```text
01. Foundations
→ Model / Tool / Agent Loop

02. RAG
→ External Knowledge

03. Agent
→ Harness / Memory / Middleware / HITL

04. MCP
→ Standardized Tool Integration

05. LangGraph Core
→ State / Node / Routing / Loop / Send / Command

06. Multi-Agent
→ Router / Supervisor / Subagent / Context Isolation

07. Multi-Agent Workflow Runtime
→ Streaming / Persistence / HITL / Time Travel / Recovery
```

最后记住：

> **LangGraph 的真正价值不只是“把 Agent 连成图”，而是让长期运行的 Agent Workflow 拥有显式状态、可观察执行、持久化检查点、人工控制和可重演历史。**
