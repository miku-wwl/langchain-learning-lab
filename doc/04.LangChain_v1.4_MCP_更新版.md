# 一、MCP 快速上手：先建立正确的三层模型

MCP = Model Context Protocol。它解决的是：**AI 应用怎样用统一协议发现并调用外部能力。**

不要把 MCP 理解成“模型本身的一种能力”。更准确的结构是：

```text
User
  ↓
MCP Host / Agent Application
  ├─ LLM / Agent Runtime
  └─ MCP Client
          ↓
      MCP Protocol
          ↓
      MCP Server
      ├─ Tools
      ├─ Resources
      └─ Prompts
```

三个角色：

- **Host**：真正面向用户的 AI 应用，例如 IDE Agent、桌面客户端或你自己的 LangChain 应用。
- **Client**：Host 内部负责与某个 MCP Server 通信的协议客户端。
- **Server**：向 Client 暴露 Tools / Resources / Prompts 的服务端。

最重要的边界：

> MCP 负责“如何发现、描述和调用外部能力”；LLM / Agent Runtime 负责“什么时候使用这些能力以及如何继续任务”。

## 1.1 MCP 不只包含 Tool

MCP Server 可以暴露：

- **Tools**：可执行动作，例如计算、查询、写入、调用业务 API。
- **Resources**：可读取的数据或内容。
- **Prompts**：服务端提供的可复用提示模板。

本课程后续 Agent 学习最需要的是 Tools，因此 04 章以 Tool 为主，但不要形成“MCP = Tool Calling”的错误认知。

## 1.2 安装当前依赖

```bash
python -m pip install -U "langchain[mcp]==1.4.2" "mcp>=2,<3" langchain-openai
```

解释：

- `langchain[mcp]`：安装 LangChain 一方 MCP 集成需要的依赖。
- `mcp>=2`：当前官方 MCP Python SDK v2。
- `langchain-openai`：仅用于连接你本机的 OpenAI-compatible Foundry Local endpoint，不代表必须调用 OpenAI 云服务。

# 二、MCP 的工作机制：它和 Tool Calling 到底是什么关系？

03 章已经学过普通 Agent Tool Calling：

```text
User
 ↓
Model
 ↓
AIMessage(tool_calls)
 ↓
Agent Runtime
 ↓
Python Tool
 ↓
ToolMessage
 ↓
Model
 ↓
Final Answer
```

如果 Tool 是直接写进 Agent 代码里的，Agent 与 Tool 之间耦合很强。

接入 MCP 后：

```text
User
 ↓
Model
 ↓
Tool Call
 ↓
Agent Runtime
 ↓
LangChain MCP Adapter
 ↓
MCP Client
 ↓
MCP Server
 ↓
Tool
 ↓
Result
 ↓
Agent Runtime
 ↓
Model
 ↓
Final Answer
```

## 2.1 MCP 没有取代 Tool Calling

模型仍然需要产生 Tool Call；Agent Runtime 仍然负责执行与循环。

MCP 真正增加的是：

```text
过去：Agent A → A 自己写的 Tool Adapter → Service B
现在：Agent A → 标准 MCP Client → MCP Server B
```

因此 MCP 最核心的工程价值之一是：**减少每个 Agent 对每个外部系统都写一套专用 Adapter 的需求。**

## 2.2 MCP Server 不是“让模型直接操作机器”

Server 只暴露它明确声明的能力。真正能做什么，取决于 Server 的代码与权限。

所以安全边界仍然是：

- 谁提供这个 Server？
- Server 代码会执行什么？
- 它拿到了哪些文件、网络、数据库、凭证权限？
- 高风险 Tool 是否需要审批？

“用了 MCP”不等于“安全”。

# 三、当前两种标准传输：STDIO 与 Streamable HTTP

当前 MCP 标准传输重点掌握两个：

```text
Local                         Remote / Deployed
─────                         ─────────────────
STDIO                         Streamable HTTP
Client 启动 Server 子进程      Server 独立运行
stdin/stdout JSON-RPC          HTTP POST 到 /mcp
适合本机工具                   适合网络服务
```

旧 SSE transport 仍可能在历史服务中出现，但新实现不要优先选择它。

## 3.1 STDIO

STDIO 的准确工作模式：

```text
MCP Client
   │
   ├─ spawn subprocess
   ↓
MCP Server Process
   ↑            ↓
stdin        stdout
   \          /
    JSON-RPC
```

关键规则：

- Client 启动 MCP Server 子进程。
- Client 把 MCP JSON-RPC 写到 Server 的 `stdin`。
- Server 把 MCP JSON-RPC 写到 `stdout`。
- Server 的普通日志应该写 `stderr`，不要 `print()` 污染 stdout 协议流。
- 子进程环境变量应显式传入，不应默认把整个用户环境泄露给未知 Server。

STDIO 很适合：本地文件工具、CLI 工具、开发期 Server、桌面/IDE Host。

## 3.2 Streamable HTTP

当前 2026-07-28 规范不要再把 Streamable HTTP 简化成“一个长期 HTTP 长连接”。

更准确的理解：

```text
MCP Client
    ↓
POST /mcp  (JSON-RPC request)
    ↓
MCP Server
    ↓
response:
  JSON
  或 request-scoped SSE stream
```

重点：

- Client 的每条消息使用新的 HTTP POST。
- Server 可以直接返回 JSON，也可以为这一次请求返回 SSE stream。
- 当前协议已经向无状态方向演进；现代实现不应该依赖旧的协议级 session 绑定。

Streamable HTTP 更适合：远程服务、团队共享服务、部署后的 MCP Server。

## 3.3 如何选择？

| 场景 | 优先选择 |
|---|---|
| 本地学习 / CLI | STDIO |
| 本机脚本作为工具 | STDIO |
| 单元测试 | In-process（SDK 测试模式） |
| 远程部署 | Streamable HTTP |
| 新系统 | 不建议从旧 SSE 开始 |

# 四、先不接 Agent：自己写 MCP Server + Client

这是本章最重要的教学变化：**先证明 MCP 协议链路本身工作，再把它交给 Agent。**

## 4.1 官方 Python SDK v2：写一个最小 MCP Server

```python
# mcp_server.py
from mcp.server import MCPServer

mcp = MCPServer("learning-demo")


@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two integers."""
    return a + b


@mcp.tool()
def get_course_stage() -> str:
    """Return the current learning stage."""
    return "04. MCP"


@mcp.resource("course://summary")
def course_summary() -> str:
    """A tiny resource used to demonstrate MCP resources."""
    return "This chapter studies MCP clients, servers, transports, and LangChain integration."


@mcp.prompt()
def explain_mcp(audience: str = "beginner") -> str:
    """Return a reusable prompt for explaining MCP."""
    return f"Explain MCP to a {audience} using one simple architecture diagram."


if __name__ == "__main__":
    # Default transport: stdio
    mcp.run()
```

和旧教程相比，一个重要更新是：官方 `mcp` Python SDK v2 已经把旧的高层 `FastMCP` 类改名为 `MCPServer`。

## 4.2 原生 MCP Client：验证 Tool Discovery

```python
# raw_stdio_client.py
import asyncio
import sys
from pathlib import Path

from mcp import Client, StdioServerParameters

SERVER = Path(__file__).with_name("mcp_server.py").resolve()


async def main() -> None:
    params = StdioServerParameters(
        command=sys.executable,
        args=[str(SERVER)],
    )

    async with Client(params) as client:
        result = await client.list_tools()
        print([tool.name for tool in result.tools])

        answer = await client.call_tool("add", {"a": 2, "b": 3})
        print(answer.structured_content)


asyncio.run(main())
```

这一段要观察两个动作：

```text
list_tools()
    ↓
Client 发现 Server 暴露了什么

call_tool(...)
    ↓
Client 按协议调用其中一个 Tool
```

这就是 MCP 最核心的“发现 + 调用”能力。

## 4.3 为什么先做 Raw Client？

因为这样你能证明：

```text
MCP Server
↕
MCP Client
```

本身已经 E2E 成功。

后面 Agent 失败时，你就能区分：

- 是 MCP transport / server 有问题；还是
- 是 LLM 没产生正确 Tool Call；还是
- 是 Agent Runtime / Adapter 层有问题。

这比直接把所有东西揉成一个 Agent 更容易学习和排错。

# 五、LangChain v1.4：使用一方 MCPAdapter

这是原 PDF 变化最大的一块。

LangChain 1.4 已经把 MCP 接入能力放进一方命名空间：

```python
from langchain.mcp import MCPAdapter
```

旧的 `langchain-mcp-adapters` 曾经是主流方式，但其仓库已经归档。新学习代码优先使用 `langchain.mcp`。

## 5.1 Local-first 模型工厂

本章继续复用 Foundry Local / 其他本地 OpenAI-compatible endpoint：

```python
# model_factory.py
import os
from langchain_openai import ChatOpenAI


def build_local_model() -> ChatOpenAI:
    return ChatOpenAI(
        model=os.environ["LOCAL_MODEL"],
        base_url=os.environ["LOCAL_LLM_BASE_URL"],
        api_key="none",
        temperature=0,
    )
```

模型必须支持 Tool Calling，否则 MCP Server 正常也不代表 Agent 一定会调用 Tool。

## 5.2 STDIO：LangChain Agent → Local MCP Server

注意：LangChain v1.4 为了安全，`MCPAdapter` 的普通字符串 target 被解释为 HTTP(S) URL。要明确启动本地脚本，应使用 `Path`（或显式 MCP 配置），而不是把 Windows 路径当普通字符串传入。

```python
# agent_stdio.py
import asyncio
from pathlib import Path

from langchain.agents import create_agent
from langchain.mcp import MCPAdapter

from model_factory import build_local_model


async def main() -> None:
    server = Path(__file__).with_name("mcp_server.py").resolve()

    adapter = MCPAdapter(server)
    tools = await adapter.list_tools()

    print("Discovered MCP tools:", [tool.name for tool in tools])

    agent = create_agent(
        model=build_local_model(),
        tools=tools,
        system_prompt="Use available tools when they are required to answer accurately.",
    )

    result = await agent.ainvoke({
        "messages": [{"role": "user", "content": "请用工具计算 37 + 58"}]
    })

    for message in result["messages"]:
        print(type(message).__name__, message.content)


asyncio.run(main())
```

完整链路：

```text
User
 ↓
Local LLM
 ↓
AIMessage(tool_call: add)
 ↓
LangChain Agent Runtime
 ↓
MCPAdapter
 ↓
STDIO MCP Client
 ↓
Local MCP Server
 ↓
add(37, 58)
 ↓
Tool result
 ↓
Local LLM
 ↓
Final Answer
```

## 5.3 Streamable HTTP

把同一个 Server 改成 HTTP 运行：

```python
if __name__ == "__main__":
    mcp.run(
        transport="streamable-http",
        host="127.0.0.1",
        port=8000,
    )
```

然后 LangChain 侧只需要改 target：

```python
from langchain.mcp import MCPAdapter

adapter = MCPAdapter("http://127.0.0.1:8000/mcp")
tools = await adapter.list_tools()
```

上层 Agent 代码基本不用变化：

```text
Agent
 ↓
MCPAdapter
 ↓
STDIO            或            Streamable HTTP
 ↓                              ↓
Local process                 Remote service
```

这也是协议抽象的价值：**调用者关注 MCP 能力，而不是每个业务服务都重新设计专用调用方式。**

## 5.4 MCPAdapter 现在帮你做什么？

核心可以理解为：

```text
MCP Tool Schema
      ↓
MCPAdapter
      ↓
LangChain BaseTool
      ↓
create_agent(..., tools=...)
```

`list_tools()` 会发现远端 MCP Tools，并转成 LangChain 可以直接使用的异步 Tool。

到这一层后，Model 看到的仍然是 Tool Schema；它并不需要理解 MCP 协议细节。

# 六、Tools / Resources / Prompts 的边界

为了避免“学了 MCP 之后只知道 Tool”，这一节保留最小认知：

```text
MCP Server
├─ Tools       → 做事情
├─ Resources   → 给数据 / 内容
└─ Prompts     → 给可复用提示模板
```

例如：

- `add(a, b)` 是 Tool。
- `course://summary` 是 Resource。
- `explain_mcp(audience)` 是 Prompt。

LangChain 的 `MCPAdapter` 这一章主要用于把 **Tools** 变成 LangChain Tools。

如果你要直接操作 Resources / Prompts，可以使用底层 MCP Client（或 `adapter.client` 做更高级的 MCP 操作）。

本章不用把所有 MCP feature 一次学完。先把 Tool Discovery / Tool Call / Transport / Agent Integration 做扎实。

# 七、当前协议版本需要知道到什么程度？

本章不需要背 MCP specification，但要知道旧资料可能出现两代行为。

## 7.1 现代协议（2026-07-28）

当前协议已经明显向无状态模式演进，例如：

- 现代 Client / Server 可以使用新的 discovery 流程。
- Streamable HTTP 不再依赖旧式协议 session 绑定。
- 每个 HTTP 请求带上所需的协议元信息。

当前 SDK 会处理版本协商 / 兼容，普通应用代码通常不用自己实现。

## 7.2 为什么旧教程还能看到 initialize / session / SSE？

因为现实世界仍然存在旧 MCP Server。

学习时记住：

```text
新项目：优先当前 SDK + STDIO / Streamable HTTP
旧服务：可能需要兼容 legacy handshake / SSE
```

不要为了兼容旧资料，把新项目主动写回旧协议风格。

# 八、MCP 安全：04 章必须建立的工程意识

MCP 的易用性很强，因此安全边界反而更重要。

## 8.1 STDIO Server = 本机代码执行边界

安装/运行未知 STDIO Server，本质上是在你的电脑启动别人提供的进程。

因此：

- 不运行来源不明的 Server。
- 不把整个环境变量无脑传给子进程。
- Secret 使用显式 allowlist / `env=`。
- 给文件系统和网络访问设最小权限。

## 8.2 Remote MCP = 外部服务边界

Streamable HTTP 至少考虑：

- HTTPS
- Authentication / Authorization
- Token 生命周期
- 超时与错误处理
- Server identity / allowlist
- 敏感 Tool 的权限分级

## 8.3 Tool Description 不是安全策略

不要指望在 Tool description 中写：

```text
“请不要删除重要数据”
```

就能形成真正的安全边界。

真正高风险操作应使用确定性代码控制，例如：

```text
Agent proposes destructive MCP Tool
             ↓
        Approval Policy
             ↓
        Human Approval
        /            \
    approve          reject
       ↓                ↓
 execute              stop
```

也就是说：03 的 HITL 与 04 的 MCP 并不是两件独立的事。真实系统中，**MCP 负责提供能力，HITL / Guardrails 负责约束能力。**
