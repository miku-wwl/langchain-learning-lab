# 03. 使用 LangChain v1.4 构建简单 Agent（更新版）

> 基线：LangChain 1.4.2 / Python >= 3.10 / Local-first
>
> 本章更新目标：保留原课程“Chat Agent → Tools → Memory → HITL → Skill”的主线，修正过时 API 和表述，并改成可以本地验证的学习版本。

## 课程目标

- 理解当前 LangChain 对 Agent 与 Harness 的定义。
- 使用 `create_agent()` 构建最小聊天 Agent。
- 理解 Tools、Tool Calling、Tool Error Handling。
- 理解短期记忆、`thread_id`、Agent State、Context、Store 的区别。
- 使用 Middleware 完成 PII、消息压缩和工具错误处理。
- 使用 Human-in-the-Loop 对高风险工具调用做审批。
- 理解 Skill 的“渐进式披露”；知道 Deep Agents 已提供正式 Skills 能力。

## 0. v1.4 更新重点

| 原课程中的理解/写法 | v1.4 更新后的建议 |
|---|---|
| 把 `create_agent` 主要描述成 LangGraph Agent | `create_agent` 是 LangChain 的高层 Agent Harness，底层运行在 LangGraph runtime 上 |
| 主要讲 `stream_mode` | `stream_mode` 仍可用；新应用优先了解 `stream_events()` typed projections |
| 工具异常主要手写 `wrap_tool_call` | 常见场景优先用 `ToolErrorMiddleware` / `ToolRetryMiddleware` |
| “外部 Checkpointer 需要自己实现” | 已有 Postgres、Redis、MongoDB 等官方/集成实现；本地教学继续用 `InMemorySaver` |
| HITL 通过 `__interrupt__` 字段手工判断 | v1.4 推荐 `version="v2"`，读取 `result.interrupts`，再用 `Command(resume=...)` 恢复 |
| Skill 只能自行模拟 | Deep Agents 已正式支持 `SKILL.md` + progressive disclosure；自定义模拟仍适合理解原理 |

# 一、Agent 到底是什么？

当前官方文档给出的核心定义非常直接：

**Agent = 模型反复调用工具，直到任务完成。**

而 **Harness** 是围绕这个循环的所有控制层：Prompt、Tools、Middleware、Memory/State、Guardrails 等。

```text
User
  ↓
Agent Harness
  ├─ System Prompt
  ├─ Tools
  ├─ Middleware
  ├─ State / Checkpointer
  └─ Guardrails / HITL
        ↓
      Model
        ↓
  Tool call? ── Yes ─→ Tool → ToolMessage ─┐
        │                                   │
        No                                  └→ Model again
        ↓
   Final Answer
```

因此，Agent 不是一个“特殊模型”，而是一种运行模式：模型在 Harness 的约束下循环观察、选择工具、执行、继续推理，直到结束。

`create_agent()` 是 LangChain v1.4 推荐的高层入口。它返回一个已经编译好的、基于 LangGraph runtime 的 Agent Graph。

# 二、构建最小聊天 Agent

## 2.1 Local-first 模型

本章不要求 OpenAI、Bedrock、DashScope 等付费 API。优先使用本机 Foundry Local / Ollama / 其他 OpenAI-compatible endpoint。

先检查本机：

```bash
foundry --version
foundry server status
foundry model list --cached
foundry model list --loaded
```

Foundry Local 的 REST 服务兼容 OpenAI Chat Completions。端口可能动态变化，所以不要把端口写死在教程里；从 `foundry server status` 获取本地 endpoint。

```python
# model_factory.py
import os
from langchain_openai import ChatOpenAI


def build_local_model() -> ChatOpenAI:
    return ChatOpenAI(
        model=os.environ["LOCAL_MODEL"],
        base_url=os.environ["LOCAL_LLM_BASE_URL"],
        api_key="none",
        temperature=0,
    )
```

`.env` 示例：

```text
LOCAL_MODEL=phi-4-mini
LOCAL_LLM_BASE_URL=http://127.0.0.1:<PORT>/v1
```

> 选择模型时，优先选 Foundry Local 列表中 `Tools = supported` 的模型，否则后面的 Tool Calling 可能失败。

## 2.2 create_agent

```python
from langchain.agents import create_agent
from model_factory import build_local_model

llm = build_local_model()

agent = create_agent(
    model=llm,
    tools=[],
    system_prompt=(
        "你是一位经验丰富的 IT 讲师。"
        "回答要准确、简洁；不知道时明确说不知道。"
    ),
)

result = agent.invoke({
    "messages": [{"role": "user", "content": "你能帮我做什么？"}]
})
print(result["messages"][-1].content)
```

这里要理解：`system_prompt`、模型、工具、Middleware 都属于 Harness，而不是模型本身。

## 2.3 Streaming

v1.4 中传统 `stream()` 仍可使用，例如观察每一步 Agent progress：

```python
for chunk in agent.stream(
    {"messages": [{"role": "user", "content": "介绍一下 LangChain Agent"}]},
    stream_mode="updates",
    version="v2",
):
    print(chunk)
```

常见模式：

- `updates`：每个 Agent step 的状态更新。
- `messages`：LLM token + metadata。
- `custom`：工具或节点主动写出的自定义进度。

**v1.4 提醒：** 对新应用，官方更推荐了解 `stream_events()` typed-projection API，因为它可以把 message、tool calls、values 等投影分别消费；本章只需要先掌握 `stream()` 的基本感觉。

## 2.4 PII Guardrail

```python
from langchain.agents import create_agent
from langchain.agents.middleware import PIIMiddleware

agent = create_agent(
    model=llm,
    tools=[],
    middleware=[
        PIIMiddleware("email", strategy="redact", apply_to_input=True),
        PIIMiddleware("credit_card", strategy="mask", apply_to_input=True),
    ],
)

result = agent.invoke({
    "messages": [{
        "role": "user",
        "content": "邮箱 john.doe@example.com，信用卡 5105-1051-0510-5100",
    }]
})
```

`PIIMiddleware` 是 Middleware 的典型例子：它不是模型能力，而是在 Agent Loop 外围对输入/输出进行治理。

# 三、给 Agent 增加 Tools

## 3.1 Tool Calling 的完整链路

```text
User
  ↓
Model
  ↓
AIMessage(tool_calls=[...])
  ↓
Tool execution
  ↓
ToolMessage(result)
  ↓
Model
  ↓
Final Answer
```

在 01 中我们手写过 Tool Loop；在 03 中要理解 `create_agent()` 已经把这个循环封装起来。

## 3.2 最小 Tool

```python
import datetime
from langchain.agents import create_agent
from langchain.tools import tool

@tool
def get_current_date() -> str:
    """获取今天日期。"""
    return datetime.date.today().isoformat()

agent = create_agent(
    model=llm,
    tools=[get_current_date],
)

result = agent.invoke({
    "messages": [{"role": "user", "content": "今天日期是什么？"}]
})
print(result["messages"][-1].content)
```

关键点：模型并不直接执行 Python。模型只提出 Tool Call，Agent Runtime 负责执行工具，并把结果作为 `ToolMessage` 放回循环。

## 3.3 Tool 返回值

v1.4 常见返回方式：

- `str`：自然语言结果。
- `dict/object`：结构化数据，交给模型继续读取。
- `Command`：不仅返回结果，还更新 Agent State。
- `return_direct=True`：直接短路 Agent Loop，把工具结果返回调用方。

## 3.4 工具异常：优先使用 ToolErrorMiddleware

原教程用自定义 `wrap_tool_call` 手工捕获异常。v1.4 常见场景更建议直接使用 `ToolErrorMiddleware`。

```python
from langchain.agents import create_agent
from langchain.agents.middleware import ToolErrorMiddleware, ToolCallRequest
from langchain.tools import tool

@tool
def divide(a: int, b: int) -> float:
    """计算 a / b。"""
    if b == 0:
        raise ZeroDivisionError("division by zero")
    if b == 1:
        raise ValueError("教学案例：b 不能为 1")
    return a / b


def on_tool_error(exc: Exception, request: ToolCallRequest) -> str | None:
    if isinstance(exc, ZeroDivisionError):
        return "除数不能为 0，请修改参数后重试。"
    if isinstance(exc, ValueError):
        return "参数不满足工具约束，请重新选择参数。"
    return None  # 未处理的异常继续抛出

agent = create_agent(
    model=llm,
    tools=[divide],
    middleware=[ToolErrorMiddleware(on_error=on_tool_error)],
)
```

如果工具调用依赖网络，并且错误可能是暂时性的，可以再组合 `ToolRetryMiddleware`；“错误转换”和“自动重试”是两个不同职责。

# 四、短期记忆、State、Context 与 Store

## 4.1 Checkpointer + thread_id

短期记忆的核心不是“模型自动记住”，而是 Harness 把同一个 thread 的历史状态持久化，再在后续运行中恢复。

```python
from langchain.agents import create_agent
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model=llm,
    tools=[],
    checkpointer=InMemorySaver(),
)

config = {"configurable": {"thread_id": "demo-thread-1"}}

agent.invoke(
    {"messages": [{"role": "user", "content": "我叫 Alice。"}]},
    config=config,
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "我叫什么？"}]},
    config=config,
)
print(result["messages"][-1].content)
```

换一个 `thread_id`，就应该形成独立会话。

> `InMemorySaver` 适合学习和测试。生产环境已经有 Postgres 等持久化 Checkpointer，不再需要从零自己实现。

## 4.2 三个概念不要混

| 概念 | 生命周期 | 典型用途 |
|---|---|---|
| State | 当前对话 / thread | messages、计数器、中间状态 |
| Context | 单次调用传入、只读 | user_id、session 信息、请求级配置 |
| Store | 跨对话长期持久化 | 用户偏好、长期记忆、共享数据 |

`thread_id` 负责给 Checkpointer 划分会话；它不是用户 ID，也不是长期记忆的 Key。

## 4.3 ToolRuntime 访问 State

```python
from langchain.agents import AgentState, create_agent
from langchain.tools import tool, ToolRuntime

class CustomState(AgentState):
    user_id: str

@tool
def get_user_info(runtime: ToolRuntime) -> str:
    """根据当前 Agent State 查询用户信息。"""
    user_id = runtime.state["user_id"]
    return f"当前用户 ID: {user_id}"

agent = create_agent(
    model=llm,
    tools=[get_user_info],
    state_schema=CustomState,
)

result = agent.invoke({
    "messages": [{"role": "user", "content": "查询我的用户信息"}],
    "user_id": "user_123",
})
```

`runtime` 参数不会暴露给模型的 Tool Schema；它由运行时自动注入。

## 4.4 Trim：直接裁剪旧消息

```python
from typing import Any
from langchain.agents import AgentState, create_agent
from langchain.agents.middleware import before_model
from langchain.messages import RemoveMessage
from langgraph.graph.message import REMOVE_ALL_MESSAGES
from langgraph.runtime import Runtime

@before_model
def trim_messages(state: AgentState, runtime: Runtime) -> dict[str, Any] | None:
    messages = state["messages"]
    if len(messages) <= 6:
        return None

    # 教学版：保留第一条 + 最近 4 条
    new_messages = [messages[0], *messages[-4:]]
    return {
        "messages": [
            RemoveMessage(id=REMOVE_ALL_MESSAGES),
            *new_messages,
        ]
    }
```

注意：工具调用消息必须保持合法配对。不要随意留下一个带 tool call 的 AIMessage，却删除对应的 ToolMessage。

## 4.5 Summarization：把旧历史压缩成摘要

```python
from langchain.agents.middleware import SummarizationMiddleware
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model=llm,
    tools=[],
    middleware=[
        SummarizationMiddleware(
            model=llm,
            trigger=("messages", 10),
            keep=("messages", 4),
        )
    ],
    checkpointer=InMemorySaver(),
)
```

Trim 是“删掉”；Summarization 是“用模型把旧上下文压缩成摘要”。两者解决的是同一个上下文膨胀问题，但保真度与成本不同。

# 五、Human-in-the-Loop（HITL）

HITL 的目的不是“让人一直盯着 Agent”，而是在高风险动作真正执行前，把控制权交还给人。

```text
User
 ↓
Agent
 ↓
Model proposes tool call
 ↓
HITL policy
 ├─ safe tool ─────────────→ execute
 └─ risky tool → interrupt → human decision
                              ├─ approve
                              ├─ edit
                              ├─ reject
                              └─ respond
```

## 5.1 定义安全与高风险工具

```python
from langchain.tools import tool

@tool
def read_data(key: str) -> str:
    """读取数据。"""
    return f"value for {key}"

@tool
def execute_sql(query: str) -> str:
    """执行 SQL。教学案例，不连接真实数据库。"""
    return f"SIMULATED SQL: {query}"
```

## 5.2 配置 HumanInTheLoopMiddleware

```python
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model=llm,
    tools=[read_data, execute_sql],
    middleware=[
        HumanInTheLoopMiddleware(
            interrupt_on={
                "read_data": False,
                "execute_sql": {
                    "allowed_decisions": ["approve", "reject"],
                },
            },
            description_prefix="Tool execution pending approval",
        )
    ],
    checkpointer=InMemorySaver(),
)
```

HITL 必须搭配 Checkpointer，因为 Agent 要能够在中断时保存状态，并在之后恢复。

## 5.3 v1.4 推荐的 interrupt / resume

```python
from langgraph.types import Command

config = {"configurable": {"thread_id": "hitl-demo"}}

result = agent.invoke(
    {
        "messages": [{
            "role": "user",
            "content": "执行 SQL: DELETE FROM users WHERE inactive = true",
        }]
    },
    config=config,
    version="v2",
)

if result.interrupts:
    print(result.interrupts)

    # 示例：人工批准
    resumed = agent.invoke(
        Command(resume={"decisions": [{"type": "approve"}]}),
        config=config,
        version="v2",
    )
```

v1.4 内置四类决策：

- `approve`：按原参数执行。
- `edit`：修改工具参数后执行。
- `reject`：拒绝执行，并把反馈交回 Agent。
- `respond`：人直接充当这个“工具”的结果提供者，适合 ask-user 类型工具。

对于有副作用的工具，拒绝时优先用 `reject`，不要用 `respond` 假装执行成功。

# 六、Skill：从“手写模拟”到 Deep Agents 正式能力

原教程通过 Middleware + `load_skill()` 手写“渐进式披露”，用来解释 Skill 的工作原理。这个教学思路仍然有价值。

但到 v1.4 生态中，需要补充一个重要变化：**Deep Agents 已正式支持 Skills。** 每个 Skill 放在独立目录中，以 `SKILL.md` 为核心；启动时只读取 frontmatter/描述，真正需要时再加载完整内容，这就是 progressive disclosure。

```text
skills/
└─ ai_teacher/
   ├─ SKILL.md
   ├─ scripts/
   └─ references/
```

`SKILL.md` 的核心思想：

```markdown
---
name: ai_teacher
description: 当用户询问 AI 学习路线、课程规划时使用
---

# AI Teacher

这里放完整流程、约束、参考资料和操作步骤。
```

## 6.1 为什么还要理解手写版？

因为手写版能让你看清底层机制：

```text
User request
    ↓
System prompt contains skill summaries only
    ↓
Model decides a skill is relevant
    ↓
load_skill(name)
    ↓
Full skill content enters context
    ↓
Model continues task
```

这本质上是在做 **Context Engineering**：把“所有知识全部塞进 Prompt”改成“需要时再加载”。

## 6.2 教学版最小 load_skill Tool

```python
from langchain.tools import tool

SKILLS = {
    "ai_teacher": {
        "description": "AI 学习路线与课程规划",
        "content": "先评估基础，再按 LLM -> RAG -> Agent -> LangGraph 设计路线。",
    }
}

@tool
def load_skill(skill_name: str) -> str:
    """按名称加载完整 Skill 内容。"""
    skill = SKILLS.get(skill_name)
    if not skill:
        return f"Unknown skill: {skill_name}"
    return skill["content"]
```

真正使用 Deep Agents 时，不需要在 03 章重复造完整 Skill 系统；这里的目的只是理解“渐进式披露”为什么能降低上下文成本。

# 七、03 章应该形成的完整认知

```text
               ┌───────────────┐
               │   User Input  │
               └───────┬───────┘
                       ↓
               ┌───────────────┐
               │ Agent Harness │
               │ prompt        │
               │ middleware    │
               │ state         │
               │ checkpointer  │
               └───────┬───────┘
                       ↓
                   ┌───────┐
                   │ Model │
                   └───┬───┘
                       ↓
                  tool call?
                 /          \
               no            yes
               ↓              ↓
          final answer       Tool
                              ↓
                       ToolMessage
                              ↓
                       middleware
                       /         \
                    normal       HITL
                      ↓           ↓
                    Model    human decision
```

真正需要掌握的不是 API 数量，而是边界：

- **Model**：决定下一步该说什么/调用什么。
- **Tool**：连接确定性代码和外部能力。
- **Agent Harness**：控制模型如何循环。
- **Middleware**：在关键生命周期点注入治理逻辑。
- **Checkpointer + thread_id**：短期会话状态与恢复。
- **State / Context / Store**：不同生命周期的数据。
- **HITL**：副作用发生前，把控制权交给人。
- **Skill**：按需加载复杂知识与工作流说明。

## 推荐本地 E2E Stage

```text
Stage A  create_agent 基础聊天
Stage B  Streaming + PII
Stage C  Tool Calling
Stage D  Tool Error Middleware
Stage E  Short-term Memory + thread isolation
Stage F  Agent State + ToolRuntime
Stage G  Trim / Summarization
Stage H  Human-in-the-Loop
Stage I  Skill progressive disclosure（教学版）
```

每一个 Stage 都应该：真实运行 → 观察消息/状态 → 验证行为 → 再进入下一 Stage。

# 八、章节总结

03 的核心不是“再学一个 create_agent API”，而是理解 Agent Harness 的工程边界。

到这里，你应该能够解释：

1. `bind_tools` 为什么不等于 Agent。
2. 模型产生 tool call 后，谁真正执行 Python Tool。
3. Middleware 为什么是 Harness，而不是 Model 能力。
4. `thread_id` 为什么是会话隔离键，而不是长期记忆本身。
5. State、Context、Store 各自应该放什么。
6. HITL 为什么必须配合持久化状态。
7. Skill 为什么本质上是一种按需 Context Engineering。

下一章 04 再进入 MCP：它解决的重点不是“Agent 会不会调用 Tool”，而是 **Tool 如何被标准化、跨进程/跨应用复用和发现**。
