# 二、使用 LangChain v1.4 构建 RAG 应用

> 基于原《2、使用LangChain构建RAG应用》更新。  
> **版本基线：LangChain 1.4.x；本文按 1.4.2 编写（2026-09-23 核验）。**  
> Python 要求：**Python >= 3.10，< 4.0**。  
> 本章默认采用 **Local-first**：聊天模型优先使用本地 OpenAI-compatible endpoint（如 Foundry Local），向量检索优先使用本地 Embedding + `InMemoryVectorStore`。

上一章节已经跑通 LangChain 的 Model、Prompt、Tool、Agent 和短期记忆。本章继续沿用“**理解 -> 最小实现 -> 本地运行 -> E2E 验证**”的学习方式，用 RAG（Retrieval-Augmented Generation，检索增强生成）把外部知识接入大模型。

> 一个重要更新：**RAG 本身不等于 Agent。**  
> 最基础的 RAG 可以完全是确定性的 Pipeline：`Load -> Split -> Embed -> Retrieve -> Prompt -> LLM`。只有当“是否检索、检索哪个知识库、是否重试、是否调用其他工具”等决策交给模型时，才进入 **Agentic RAG / RAG Agent**。

- 为后续 Agent / MCP / LangGraph 学习准备“知识检索”基础能力

# 一、RAG 基础流程

## 1、为什么需要 RAG？

直接向大模型提问时，模型只能依靠训练阶段学到的知识以及当前 Prompt 中已有的信息。

例如企业内部的退款规则、运维手册、产品文档、内部 API 说明等，模型通常并不知道，或者知道的信息已经过期。

常见的两条路线是：

- **Fine-tuning（微调）**：修改模型行为或让模型更好地适应某类任务、格式和领域表达。
- **RAG**：在推理时把与当前问题最相关的外部知识检索出来，再提供给模型。

二者不是互斥关系。一个系统可以同时使用微调和 RAG。

对于“企业知识经常变化、文档很多、需要知道答案来源”的场景，RAG 通常是更自然的第一步。

---

## 2、RAG 的两个阶段

### Indexing：索引阶段

```text
Raw Files
   ↓
Document Loader
   ↓
Documents
   ↓
Text Splitter
   ↓
Chunks
   ↓
Embedding Model
   ↓
Vectors
   ↓
Vector Store
```

这一阶段一般不是每次用户提问都重新执行，而是在知识内容发生变化时进行构建或更新。

核心步骤：

1. 把 PDF / Markdown / TXT / HTML / JSON 等数据加载成 LangChain `Document`。
2. 把长文档切成较小的 Chunk。
3. 使用 Embedding 模型把 Chunk 转成向量。
4. 把向量与原文、metadata 一起保存到 Vector Store。

### Retrieval + Generation：检索与生成阶段

```text
User Question
      ↓
Query Embedding
      ↓
Vector Search
      ↓
Top-K Relevant Chunks
      ↓
Prompt + Context
      ↓
LLM
      ↓
Answer
```

这里真正关键的是：

> **先找对资料，再让模型回答。**

如果 Retriever 找错了内容，再强的 LLM 也很难生成正确答案。

---

## 3、先看“不使用 RAG”的基线

本章不绑定付费云 API。假设你已经有一个本地 OpenAI-compatible endpoint，例如 Foundry Local。

先从环境变量读取 endpoint 和实际模型 ID：

```bash
# PowerShell 示例
$env:LOCAL_OPENAI_BASE_URL="http://127.0.0.1:<PORT>/v1"
$env:LOCAL_CHAT_MODEL="<你本机实际加载的模型ID>"
```

Foundry Local 的端口可能是动态的，先执行：

```bash
foundry server status
foundry model list --loaded
```

不要在代码中长期硬编码端口。

```python
import os
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model=os.environ["LOCAL_CHAT_MODEL"],
    base_url=os.environ["LOCAL_OPENAI_BASE_URL"],
    api_key="none",
    temperature=0,
)

response = llm.invoke("公司的退款规则是什么？")
print(response.content)
```

这一步的目的不是让模型答对，而是建立 Baseline：

```text
没有企业知识
      ↓
模型只能根据已有训练知识猜测
```

接下来 RAG 就是在这个链路中加入“外部知识检索”。

# 二、构建一个简单的 RAG 应用

本章使用一个极小的“退款规则知识库”做实验。重点是理解每一个组件，而不是搭一个大系统。

## 1、安装依赖

```bash
pip install -U "langchain==1.4.2"
pip install -U langchain-openai
pip install -U langchain-community
pip install -U langchain-text-splitters
pip install -U langchain-huggingface sentence-transformers
```

说明：

- `langchain`：Agent / 高层框架能力
- `langchain-core`：`Document`、Prompt、Vector Store 接口等核心抽象（会由 LangChain 依赖安装）
- `langchain-community`：大量社区/第三方 integration，例如 `TextLoader`
- `langchain-text-splitters`：文本切分器
- `langchain-huggingface` + `sentence-transformers`：本地 Embedding 示例
- `langchain-openai`：用于 OpenAI-compatible 本地聊天 endpoint

> 原教程使用 Redis 作为向量数据库。本更新版把 **InMemoryVectorStore** 作为主路径，这样 02 可以完全本地、无 Docker、无外部数据库地完成 E2E。Redis 放到本章最后作为可选扩展。

---

## 2、准备知识文件

创建：

```text
resources/refund_policy.txt
```

示例内容：

```text
退款规则：
1. 普通商品在签收后 7 天内可以申请退款。
2. 已拆封的软件授权、数字商品和定制商品不支持无理由退款。
3. 退款申请提交后，客服会在 2 个工作日内完成审核。
4. 审核通过后，退款原路返回，通常需要 3 到 5 个工作日到账。
5. 商品存在质量问题时，退货运费由公司承担。
```

这份文件就是我们的最小企业知识库。

---

## 3、加载文档：Document Loader

```python
from langchain_community.document_loaders import TextLoader

loader = TextLoader(
    "resources/refund_policy.txt",
    encoding="utf-8",
)

documents = loader.load()

print(type(documents[0]))
print(documents[0].page_content)
print(documents[0].metadata)
```

LangChain Loader 的输出通常是：

```python
list[Document]
```

一个 `Document` 最重要的两个成员是：

```text
page_content  -> 文本正文
metadata      -> 来源、页码、文件名等附加信息
```

RAG 后面几乎所有组件都围绕 `Document` 工作。

---

## 4、切分文档：RecursiveCharacterTextSplitter

旧教程使用 `CharacterTextSplitter`。它仍然可以使用，但对于普通自然语言文本，学习阶段更推荐先理解 `RecursiveCharacterTextSplitter`：它会按一组分隔符逐级尝试切分，通常比“只按一个字符切”更稳妥。

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=120,
    chunk_overlap=20,
    add_start_index=True,
)

chunks = splitter.split_documents(documents)

print("chunk count:", len(chunks))

for i, chunk in enumerate(chunks):
    print(f"\n--- chunk {i} ---")
    print(chunk.page_content)
    print(chunk.metadata)
```

这里要理解两个重要参数：

### `chunk_size`

每个 Chunk 的目标大小。

太大：

```text
一个 Chunk 里混入很多无关信息
→ Retrieval 精度下降
→ Prompt Token 增加
```

太小：

```text
语义被切碎
→ 检索到的信息不完整
```

### `chunk_overlap`

相邻 Chunk 保留一定重叠，避免重要语义恰好被切断。

> `chunk_size` 并不是“越小越精准”。它是 RAG 中必须通过数据与评测调优的参数。

---

## 5、文本向量化：Embedding

Embedding 的目标是：

```text
Text
 ↓
Embedding Model
 ↓
[0.018, -0.124, 0.391, ...]
```

语义相近的文本，其向量通常也更接近。

LangChain 对 Embedding 提供统一接口，最核心的两个方法是：

```python
embed_documents([...])
embed_query("...")
```

### 本地 Embedding 示例

为了让 02 可以本地验证，这里使用 Hugging Face / Sentence Transformers 的本地模型：

```python
from langchain_huggingface import HuggingFaceEmbeddings

embeddings = HuggingFaceEmbeddings(
    model_name="BAAI/bge-small-zh-v1.5",
    encode_kwargs={"normalize_embeddings": True},
)

vector = embeddings.embed_query("退款多久可以到账？")

print(type(vector))
print("dimensions:", len(vector))
print(vector[:8])
```

第一次运行通常需要下载模型；后续会复用本地缓存。

> 如果你的本机运行时已经提供可直接调用的 Embedding endpoint，可以替换这一实现。上层 Vector Store / Retriever 代码不应该依赖具体 Embedding 厂商。

---

## 6、保存向量：InMemoryVectorStore

学习阶段先不要急着上 Redis、OpenSearch、Pinecone 等数据库。

LangChain Core 提供 `InMemoryVectorStore`，非常适合本地理解 RAG：

```python
from langchain_core.vectorstores import InMemoryVectorStore

vector_store = InMemoryVectorStore(embeddings)
vector_store.add_documents(chunks)
```

现在我们已经完成 Indexing：

```text
TXT
 ↓
Document
 ↓
Chunks
 ↓
Embedding
 ↓
InMemoryVectorStore
```

---

## 7、先只做 Semantic Search

先不要接 LLM。

直接验证 Retrieval：

```python
query = "退款申请审核通过后多久能到账？"

results = vector_store.similarity_search_with_score(
    query,
    k=3,
)

for doc, score in results:
    print("score:", score)
    print(doc.page_content)
    print("metadata:", doc.metadata)
    print("---")
```

这是非常重要的一步。

不要一上来只看 LLM 的最终答案。RAG 出错时应该先问：

```text
Retriever 到底取回了什么？
```

如果 Top-K 文档就已经错了，那么问题首先在 Retrieval，而不是 Generation。

---

## 8、把 Vector Store 转成 Retriever

Vector Store 是“存储 + 搜索”的抽象。

Retriever 更接近 RAG 应用层：

```python
retriever = vector_store.as_retriever(
    search_kwargs={"k": 3}
)

retrieved_docs = retriever.invoke(
    "退款审核通过后多久能到账？"
)

for doc in retrieved_docs:
    print(doc.page_content)
```

可以这样理解：

```text
Vector Store
    ↓
相似度搜索能力

Retriever
    ↓
“给我一个 Query，返回相关 Documents”的统一接口
```

后续你换 Redis、OpenSearch、Elasticsearch 或其他检索器，上层 RAG 流程仍然可以尽量保持不变。
