# 二、使用 LangChain v1.4 构建 RAG 应用

> 基于原《2、使用LangChain构建RAG应用》更新。  
> **版本基线：LangChain 1.4.x；本文按 1.4.2 编写（2026-09-23 核验）。**  
> Python 要求：**Python >= 3.10，< 4.0**。  
> 本章默认采用 **Local-first**：聊天模型优先使用本地 OpenAI-compatible endpoint（如 Foundry Local），向量检索优先使用本地 Embedding + `InMemoryVectorStore`。

上一章节已经跑通 LangChain 的 Model、Prompt、Tool、Agent 和短期记忆。本章继续沿用“**理解 -> 最小实现 -> 本地运行 -> E2E 验证**”的学习方式，用 RAG（Retrieval-Augmented Generation，检索增强生成）把外部知识接入大模型。

> 一个重要更新：**RAG 本身不等于 Agent。**  
> 最基础的 RAG 可以完全是确定性的 Pipeline：`Load -> Split -> Embed -> Retrieve -> Prompt -> LLM`。只有当“是否检索、检索哪个知识库、是否重试、是否调用其他工具”等决策交给模型时，才进入 **Agentic RAG / RAG Agent**。

## 课程目标

- 理解 RAG 的 Indexing 与 Retrieval/Generation 两个阶段
- 理解 `Document`、Text Splitter、Embedding、Vector Store、Retriever 的职责
- 在本地构建一个最小可运行 RAG
- 掌握 LangChain v1.4 下更清晰的组件化写法
- 理解 `similarity_search()` 与 Retriever 的区别
- 理解 Chunk、Embedding、Top-K 对 RAG 质量的影响
- 为后续 Agent / MCP / LangGraph 学习准备“知识检索”基础能力

# 一、RAG 基础流程

## 1、为什么需要 RAG？

直接向大模型提问时，模型只能依靠训练阶段学到的知识以及当前 Prompt 中已有的信息。

例如企业内部的退款规则、运维手册、产品文档、内部 API 说明等，模型通常并不知道，或者知道的信息已经过期。

常见的两条路线是：

- **Fine-tuning（微调）**：修改模型行为或让模型更好地适应某类任务、格式和领域表达。
- **RAG**：在推理时把与当前问题最相关的外部知识检索出来，再提供给模型。

二者不是互斥关系。一个系统可以同时使用微调和 RAG。

对于“企业知识经常变化、文档很多、需要知道答案来源”的场景，RAG 通常是更自然的第一步。

---

## 2、RAG 的两个阶段

### Indexing：索引阶段

```text
Raw Files
   ↓
Document Loader
   ↓
Documents
   ↓
Text Splitter
   ↓
Chunks
   ↓
Embedding Model
   ↓
Vectors
   ↓
Vector Store
```

这一阶段一般不是每次用户提问都重新执行，而是在知识内容发生变化时进行构建或更新。

核心步骤：

1. 把 PDF / Markdown / TXT / HTML / JSON 等数据加载成 LangChain `Document`。
2. 把长文档切成较小的 Chunk。
3. 使用 Embedding 模型把 Chunk 转成向量。
4. 把向量与原文、metadata 一起保存到 Vector Store。

### Retrieval + Generation：检索与生成阶段

```text
User Question
      ↓
Query Embedding
      ↓
Vector Search
      ↓
Top-K Relevant Chunks
      ↓
Prompt + Context
      ↓
LLM
      ↓
Answer
```

这里真正关键的是：

> **先找对资料，再让模型回答。**

如果 Retriever 找错了内容，再强的 LLM 也很难生成正确答案。

---

## 3、先看“不使用 RAG”的基线

本章不绑定付费云 API。假设你已经有一个本地 OpenAI-compatible endpoint，例如 Foundry Local。

先从环境变量读取 endpoint 和实际模型 ID：

```bash
# PowerShell 示例
$env:LOCAL_OPENAI_BASE_URL="http://127.0.0.1:<PORT>/v1"
$env:LOCAL_CHAT_MODEL="<你本机实际加载的模型ID>"
```

Foundry Local 的端口可能是动态的，先执行：

```bash
foundry server status
foundry model list --loaded
```

不要在代码中长期硬编码端口。

```python
import os
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model=os.environ["LOCAL_CHAT_MODEL"],
    base_url=os.environ["LOCAL_OPENAI_BASE_URL"],
    api_key="none",
    temperature=0,
)

response = llm.invoke("公司的退款规则是什么？")
print(response.content)
```

这一步的目的不是让模型答对，而是建立 Baseline：

```text
没有企业知识
      ↓
模型只能根据已有训练知识猜测
```

接下来 RAG 就是在这个链路中加入“外部知识检索”。

# 二、构建一个简单的 RAG 应用

本章使用一个极小的“退款规则知识库”做实验。重点是理解每一个组件，而不是搭一个大系统。

## 1、安装依赖

```bash
pip install -U "langchain==1.4.2"
pip install -U langchain-openai
pip install -U langchain-community
pip install -U langchain-text-splitters
pip install -U langchain-huggingface sentence-transformers
```

说明：

- `langchain`：Agent / 高层框架能力
- `langchain-core`：`Document`、Prompt、Vector Store 接口等核心抽象（会由 LangChain 依赖安装）
- `langchain-community`：大量社区/第三方 integration，例如 `TextLoader`
- `langchain-text-splitters`：文本切分器
- `langchain-huggingface` + `sentence-transformers`：本地 Embedding 示例
- `langchain-openai`：用于 OpenAI-compatible 本地聊天 endpoint

> 原教程使用 Redis 作为向量数据库。本更新版把 **InMemoryVectorStore** 作为主路径，这样 02 可以完全本地、无 Docker、无外部数据库地完成 E2E。Redis 放到本章最后作为可选扩展。

---

## 2、准备知识文件

创建：

```text
resources/refund_policy.txt
```

示例内容：

```text
退款规则：
1. 普通商品在签收后 7 天内可以申请退款。
2. 已拆封的软件授权、数字商品和定制商品不支持无理由退款。
3. 退款申请提交后，客服会在 2 个工作日内完成审核。
4. 审核通过后，退款原路返回，通常需要 3 到 5 个工作日到账。
5. 商品存在质量问题时，退货运费由公司承担。
```

这份文件就是我们的最小企业知识库。

---

## 3、加载文档：Document Loader

```python
from langchain_community.document_loaders import TextLoader

loader = TextLoader(
    "resources/refund_policy.txt",
    encoding="utf-8",
)

documents = loader.load()

print(type(documents[0]))
print(documents[0].page_content)
print(documents[0].metadata)
```

LangChain Loader 的输出通常是：

```python
list[Document]
```

一个 `Document` 最重要的两个成员是：

```text
page_content  -> 文本正文
metadata      -> 来源、页码、文件名等附加信息
```

RAG 后面几乎所有组件都围绕 `Document` 工作。

---

## 4、切分文档：RecursiveCharacterTextSplitter

旧教程使用 `CharacterTextSplitter`。它仍然可以使用，但对于普通自然语言文本，学习阶段更推荐先理解 `RecursiveCharacterTextSplitter`：它会按一组分隔符逐级尝试切分，通常比“只按一个字符切”更稳妥。

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=120,
    chunk_overlap=20,
    add_start_index=True,
)

chunks = splitter.split_documents(documents)

print("chunk count:", len(chunks))

for i, chunk in enumerate(chunks):
    print(f"\n--- chunk {i} ---")
    print(chunk.page_content)
    print(chunk.metadata)
```

这里要理解两个重要参数：

### `chunk_size`

每个 Chunk 的目标大小。

太大：

```text
一个 Chunk 里混入很多无关信息
→ Retrieval 精度下降
→ Prompt Token 增加
```

太小：

```text
语义被切碎
→ 检索到的信息不完整
```

### `chunk_overlap`

相邻 Chunk 保留一定重叠，避免重要语义恰好被切断。

> `chunk_size` 并不是“越小越精准”。它是 RAG 中必须通过数据与评测调优的参数。

---

## 5、文本向量化：Embedding

Embedding 的目标是：

```text
Text
 ↓
Embedding Model
 ↓
[0.018, -0.124, 0.391, ...]
```

语义相近的文本，其向量通常也更接近。

LangChain 对 Embedding 提供统一接口，最核心的两个方法是：

```python
embed_documents([...])
embed_query("...")
```

### 本地 Embedding 示例

为了让 02 可以本地验证，这里使用 Hugging Face / Sentence Transformers 的本地模型：

```python
from langchain_huggingface import HuggingFaceEmbeddings

embeddings = HuggingFaceEmbeddings(
    model_name="BAAI/bge-small-zh-v1.5",
    encode_kwargs={"normalize_embeddings": True},
)

vector = embeddings.embed_query("退款多久可以到账？")

print(type(vector))
print("dimensions:", len(vector))
print(vector[:8])
```

第一次运行通常需要下载模型；后续会复用本地缓存。

> 如果你的本机运行时已经提供可直接调用的 Embedding endpoint，可以替换这一实现。上层 Vector Store / Retriever 代码不应该依赖具体 Embedding 厂商。

---

## 6、保存向量：InMemoryVectorStore

学习阶段先不要急着上 Redis、OpenSearch、Pinecone 等数据库。

LangChain Core 提供 `InMemoryVectorStore`，非常适合本地理解 RAG：

```python
from langchain_core.vectorstores import InMemoryVectorStore

vector_store = InMemoryVectorStore(embeddings)
vector_store.add_documents(chunks)
```

现在我们已经完成 Indexing：

```text
TXT
 ↓
Document
 ↓
Chunks
 ↓
Embedding
 ↓
InMemoryVectorStore
```

---

## 7、先只做 Semantic Search

先不要接 LLM。

直接验证 Retrieval：

```python
query = "退款申请审核通过后多久能到账？"

results = vector_store.similarity_search_with_score(
    query,
    k=3,
)

for doc, score in results:
    print("score:", score)
    print(doc.page_content)
    print("metadata:", doc.metadata)
    print("---")
```

这是非常重要的一步。

不要一上来只看 LLM 的最终答案。RAG 出错时应该先问：

```text
Retriever 到底取回了什么？
```

如果 Top-K 文档就已经错了，那么问题首先在 Retrieval，而不是 Generation。

---

## 8、把 Vector Store 转成 Retriever

Vector Store 是“存储 + 搜索”的抽象。

Retriever 更接近 RAG 应用层：

```python
retriever = vector_store.as_retriever(
    search_kwargs={"k": 3}
)

retrieved_docs = retriever.invoke(
    "退款审核通过后多久能到账？"
)

for doc in retrieved_docs:
    print(doc.page_content)
```

可以这样理解：

```text
Vector Store
    ↓
相似度搜索能力

Retriever
    ↓
“给我一个 Query，返回相关 Documents”的统一接口
```

后续你换 Redis、OpenSearch、Elasticsearch 或其他检索器，上层 RAG 流程仍然可以尽量保持不变。

---

## 9、构建 RAG Prompt

```python
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        """你是一个企业知识库问答助手。
只允许根据给定 context 回答问题。
如果 context 中没有足够信息，请明确回答：我无法根据当前知识库回答这个问题。
不要编造 context 中不存在的规则。""",
    ),
    (
        "user",
        """Context:
{context}

Question:
{question}""",
    ),
])
```

这一段 Prompt 的核心不是“让模型变聪明”，而是建立 Grounding 约束：

```text
Retrieved Context
       ↓
限制模型回答范围
       ↓
降低无依据回答
```

---

## 10、把 Retrieval 与 LLM 串起来

```python
import os
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model=os.environ["LOCAL_CHAT_MODEL"],
    base_url=os.environ["LOCAL_OPENAI_BASE_URL"],
    api_key="none",
    temperature=0,
)


def format_docs(docs):
    return "\n\n".join(
        f"[source={doc.metadata.get('source', 'unknown')}]\n{doc.page_content}"
        for doc in docs
    )


question = "退款审核通过后多久能到账？"
retrieved_docs = retriever.invoke(question)
context = format_docs(retrieved_docs)

chain = prompt | llm

response = chain.invoke({
    "context": context,
    "question": question,
})

print(response.content)
```

这就是最基础、最值得先理解的 **2-Step RAG**：

```text
Question
   ↓
Retriever
   ↓
Context
   ↓
Prompt
   ↓
LLM
   ↓
Answer
```

这里没有 Agent，也没有模型自己决定要不要检索。

这反而非常适合学习，因为整个流程是显式、可观察、可调试的。

---

## 11、验证“知识库没有答案”的情况

继续测试：

```python
question = "公司 CEO 是谁？"
retrieved_docs = retriever.invoke(question)
context = format_docs(retrieved_docs)

response = chain.invoke({
    "context": context,
    "question": question,
})

print(response.content)
```

预期行为不是“模型努力猜一个 CEO”，而应该接近：

```text
我无法根据当前知识库回答这个问题。
```

这一步是在验证：

```text
RAG != 一定要回答
```

一个可靠的知识库系统需要知道什么时候应该拒答。

# 三、解锁 LangChain v1.4 的 RAG 基础组件

原教程这一部分的方向仍然完全正确：真正理解 RAG，重点不是记住某一个 Demo，而是理解 LangChain 为每个阶段提供的抽象。

## 1、Document Loader

职责：

```text
External Data
     ↓
Document
```

LangChain 当前仍然提供大量 Loader integration。

常见例子包括：

- TXT
- PDF
- HTML
- Markdown
- CSV
- JSON
- Office 文档
- Web 页面
- 数据库 / SaaS / Object Storage

最简单文本：

```python
from langchain_community.document_loaders import TextLoader
```

复杂非结构化文件可以考虑 `UnstructuredLoader`：

```bash
pip install -U langchain-unstructured unstructured
```

```python
from langchain_unstructured import UnstructuredLoader

loader = UnstructuredLoader("resources/example.pdf")
documents = loader.load()
```

### 关于 `langchain-community`

旧教程里把 `langchain-community` 简单描述成“版本维护严重落后”并不准确。

到了 LangChain 1.x，生态更强调 **integration package 分离**：

```text
langchain-core
langchain
langchain-community
langchain-openai
langchain-huggingface
langchain-redis
...
```

学习时应该优先看当前官方文档推荐的 integration package，而不是默认认为 `langchain-community` 已经不能使用。

---

## 2、Text Splitter

职责：

```text
Long Documents
      ↓
Chunks
```

学习阶段优先掌握：

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter
```

然后再理解不同文档类型的切分策略。

真正影响 Retrieval 的不是“有没有 Split”，而是：

- Chunk 是否保持完整语义
- Chunk 大小是否合适
- 是否需要 overlap
- 标题、章节、页码等 metadata 是否保留下来

---

## 3、Embedding

职责：

```text
Text
 ↓
Semantic Vector
```

LangChain 的 Embedding interface 让不同模型使用方式尽量统一：

```python
embeddings.embed_documents([...])
embeddings.embed_query("...")
```

常见相似度度量包括：

- Cosine similarity
- Euclidean distance
- Dot product

Embedding 模型选择会直接影响 Retrieval 质量。

尤其要注意：

> **用于索引 Documents 的 Embedding 模型，与 Query 使用的 Embedding 模型必须保持兼容。**

不要索引时用一个完全不同的向量空间，查询时再换另一个模型。

---

## 4、Vector Store

职责：

```text
Vectors + Documents + Metadata
            ↓
      Similarity Search
```

本章使用：

```python
from langchain_core.vectorstores import InMemoryVectorStore
```

优点：

- 零基础设施
- 启动快
- 最适合 02 教学与 E2E

缺点：

- 进程结束数据就消失
- 不适合大量数据
- 不适合真正生产部署

实际项目再根据需求选择：

- Redis
- OpenSearch / Elasticsearch
- PostgreSQL + pgvector
- Qdrant
- Milvus
- Pinecone
- 其他 LangChain Vector Store integration

---

## 5、Retriever

Retriever 是 RAG 中很重要但经常被初学者忽略的一层。

它的核心接口非常简单：

```text
Query
 ↓
Retriever
 ↓
Documents
```

例如：

```python
retriever = vector_store.as_retriever(
    search_kwargs={"k": 3}
)

docs = retriever.invoke("退款多久能到账？")
```

为什么需要 Retriever 抽象？

因为未来你可能并不只做简单向量搜索。

Retriever 背后可以逐渐升级为：

```text
Vector Search
BM25
Hybrid Search
Metadata Filter
Reranker
Multi-query Retrieval
...
```

但是对 02 来说，只需要先把最基础 Vector Retriever 跑通。

# 四、RAG 最小质量验证

原教程最后已经指出：**“能跑起来”不等于“质量可靠”。** 这个判断非常重要。

02 不需要提前做复杂 Evaluation 平台，但至少应该形成最基础的验证意识。

## 1、先测 Retrieval，再测 Generation

推荐顺序：

```text
Question
 ↓
Top-K 文档对不对？
 ↓
如果 Retrieval 正确
 ↓
再检查最终 Answer
```

否则很容易把所有错误都归因到 LLM。

---

## 2、至少准备三类问题

### Known Answer

知识库明确存在答案：

```text
退款审核通过后多久能到账？
```

预期：相关 Chunk 应进入 Top-K，模型正确回答。

### Paraphrase

不用原文关键词：

```text
钱退回来一般还要等几天？
```

用于验证 Embedding 的语义检索能力。

### Unknown Answer

知识库没有答案：

```text
公司 CEO 是谁？
```

预期：模型拒绝编造。

---

## 3、需要观察的最小指标

教学阶段先关注：

```text
Top-K 是否包含正确 Chunk
最终回答是否被 Context 支持
无答案问题是否拒答
```

后续真正做 RAG 项目时再进一步加入：

- Hit@K / Recall@K
- MRR
- nDCG
- Faithfulness / Groundedness
- Answer correctness
- Latency

02 的目标是先知道“质量需要被测量”，不在这里展开完整 RAG Eval 系统。

# 五、可选：把 InMemoryVectorStore 换成 Redis

原教程使用 Redis，这条路线依然有价值，但不再作为 02 的默认依赖。

如果你希望验证持久化 Vector Store，可以在完成本地 InMemory E2E 后，再增加 Redis Stage。

安装：

```bash
pip install -U langchain-redis
```

推荐把它理解成：

```text
RAG Pipeline 不变
        ↓
只替换 Vector Store implementation
```

也就是说，上层：

```text
Load
Split
Embed
Retrieve
Prompt
LLM
```

不应该因为换 Redis 就全部重写。

这正是 LangChain 抽象层的价值。

# 六、02 的推荐 E2E 学习顺序

如果你让 Codex 把本章变成 Learning Lab，我建议拆成下面几个 Stage：

```text
Stage A - Baseline LLM
         不提供知识库，观察模型回答

Stage B - Document Loader
         File -> Document

Stage C - Text Splitter
         Document -> Chunks

Stage D - Embedding
         Text -> Vector

Stage E - Semantic Search
         Query -> Top-K Chunks

Stage F - Retriever
         Vector Store -> Retriever interface

Stage G - 2-Step RAG
         Retrieve -> Prompt -> LLM

Stage H - Grounding / Unknown Question
         验证拒答

Stage I - Optional Redis
         只替换 Vector Store
```

最终应该能够画出并解释：

```text
                INDEXING

File
 ↓
Loader
 ↓
Documents
 ↓
Splitter
 ↓
Chunks
 ↓
Embedding
 ↓
Vector Store


              QUERY TIME

Question
 ↓
Retriever
 ↓
Relevant Documents
 ↓
Prompt
 ↓
LLM
 ↓
Answer
```

# 七、总结

这一章最重要的不是记住某一个 Loader 或 Vector Database 的 API，而是建立 RAG 的组件模型：

```text
Document Loader
      ↓
Text Splitter
      ↓
Embedding
      ↓
Vector Store
      ↓
Retriever
      ↓
Prompt
      ↓
Model
```

其中：

- **Loader**：把外部数据转换成 `Document`
- **Splitter**：把长文档切成可检索 Chunk
- **Embedding**：把文本映射到语义向量空间
- **Vector Store**：保存并搜索向量
- **Retriever**：把 Query 转换为相关 Documents
- **Prompt**：把问题与检索内容组织给模型
- **Model**：基于给定 Context 生成回答

最基础的 RAG 是一个完全可以显式控制的 Pipeline，并不需要 Agent。

这也正是为什么 02 放在 03 Agent 之前非常合理：

> **先理解“确定性检索 + 生成”，再学习“让模型自己决定如何使用工具和检索”。**

下一章进入 Agent 后，你会看到 Tool Calling / Agent Loop 如何在这个基础上增加“决策能力”。
