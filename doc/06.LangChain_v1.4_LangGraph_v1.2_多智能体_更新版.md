# 0. 2026 更新重点

原 PDF 很短，但思路很典型：

```text
START
  ↓
“用户问题分类”
  ├─ 历史诊断记录 Agent
  ├─ 指南 RAG Agent
  ├─ 医生信息 Agent
  └─ 其他问题拒绝
        ↓
     结果汇总
        ↓
       END
```

这个架构今天仍然有学习价值，但有几个概念必须更新。

| 原 PDF 的理解 | 2026 更准确的理解 |
|---|---|
| 一个 supervisor 节点先分类，再选择一个 Agent | 如果只是“一次分类 -> 一次分发”，更准确叫 **Router** |
| Supervisor = 分类器 | Supervisor 是一个完整 Agent，可维护上下文，并在多轮中动态调用一个或多个 Subagent |
| 多智能体主要靠多个 Agent 节点拼图 | 当前常用模式包括 **Subagents-as-Tools、Router、Handoffs、Custom Workflow** |
| 可直接依赖 `langgraph-supervisor` 包 | Python `langgraph-supervisor` 仓库已于 2026-09-20 归档；新代码优先按官方多智能体指南直接实现 supervisor/subagents pattern |
| Worker Agent 把全部消息历史都拿过去 | 当前更强调 **Context Isolation**：只给 Worker 完成任务所需的信息，并尽量只把最终结果返回 Supervisor |
| 多 Agent 越多越强 | 不一定。Tool 太少、任务不复杂时，单 Agent 通常更简单、便宜、可靠 |

最重要的一条：

> **Multi-Agent 的价值不是“多几个 LLM”，而是把职责、上下文、工具和执行边界分开。**

# 一、什么时候需要 Multi-Agent？

先不要因为“多智能体”听起来高级就默认使用它。

## 1.1 单 Agent 足够的情况

如果一个 Agent 只有少量 Tool：

```text
Agent
├─ get_user_info
├─ search_guideline
└─ find_doctor
```

并且 Tool schema 很清晰，单 Agent 完全可能已经够用。

优点：

- Prompt 简单。
- Context 简单。
- Tool Calling 链路短。
- Debug 容易。
- Token 成本低。

## 1.2 Multi-Agent 更合适的情况

当出现这些情况时，再考虑拆 Worker：

- 不同领域需要完全不同的 Prompt。
- 不同领域使用不同 Tool 集合。
- 一个 Agent 的 Tool 数量已经很多，Tool Selection 开始混乱。
- 不同任务需要不同上下文。
- 想把复杂任务放到独立 context window 中执行。
- 不同团队分别开发和维护不同能力。
- 一个任务可能要并行调用多个领域专家。

可以把它理解为：

```text
单 Agent
= 一个工程师同时背着所有手册和工具

Multi-Agent
= 一个负责人按任务把工作交给不同专家
```

# 二、四个概念先分清：Router / Supervisor / Handoff / Custom Workflow

这是本章最需要更新的地方。

## 2.1 Router

Router 通常只做一次分类或分流：

```text
User Query
    ↓
  Router
 ┌──┼────┐
 ↓  ↓    ↓
A   B    C
```

例如：

```text
“查询我的历史记录” -> record_agent
“参考指南解释症状” -> guideline_agent
“有哪些医生？”     -> doctor_agent
```

Router 的特点：

- 通常是一跳分类。
- 不一定维持长期对话。
- 适合明确 domain routing。
- 可以是确定性 Python，也可以是 LLM structured output。

**原 PDF 的“用户问题分类节点”本质上更像 Router。**

## 2.2 Supervisor

Supervisor 是一个真正的 Agent：

```text
User
 ↓
Supervisor Agent
 ├─ call_record_agent(task)
 ├─ call_guideline_agent(task)
 └─ call_doctor_agent(task)
       ↓
  combine results
       ↓
     Answer
```

关键区别：Supervisor 不只是“一次分类”。它可以：

- 保持主对话上下文。
- 连续调用多个 Subagent。
- 根据第一个 Subagent 的结果决定下一步。
- 在一次模型回复中提出多个 Subagent Tool Calls。
- 最终综合多个结果。

## 2.3 Handoff

Handoff 是“控制权转移”。

```text
Sales Agent
    ↓ transfer_to_support
Support Agent
    ↓
直接继续和用户对话
```

它适合：

- 多阶段客服。
- 当前 active agent 会变化。
- 不同 Agent 都可能直接面向用户。

本章只建立概念，不把 Handoff 作为主实现；后面复杂工作流再展开。

## 2.4 Custom Workflow

如果你需要确定性的结构：

```text
Router
 ↓
Worker
 ↓
Validation
 ↓
Aggregation
 ↓
Fallback
```

那么最清晰的方式往往是直接使用 LangGraph `StateGraph` 自己编排。

这也是 05 章 Graph 能力真正进入 06 章的地方。

# 三、保留原课程案例：医疗问诊多智能体演示

为了延续原 PDF，我们仍然使用四类输入：

```text
1. 查询历史诊断记录
2. 参考指南给出信息摘要
3. 查询医生信息
4. 其他问题 -> 礼貌拒绝
```

但必须强调：

> 这是编排教学 Demo，所有病历、指南和医生数据均为模拟数据，不用于真实医疗判断。

架构更新后可以有两种实现。

## 3.1 Pattern A：Router + Worker Graph

```text
                     ┌→ Record Agent ────┐
START → Router ──────┼→ Guideline Agent ─┼→ Aggregate → END
                     ├→ Doctor Agent ────┤
                     └→ Refuse ──────────┘
```

适合学习：

- LangGraph conditional routing。
- 每次问题只进入一个领域。
- 流程明确、易调试。

## 3.2 Pattern B：Supervisor + Subagents-as-Tools

```text
User
 ↓
Supervisor
 ├─ Record Subagent
 ├─ Guideline Subagent
 └─ Doctor Subagent
       ↓
Supervisor synthesizes
       ↓
Answer
```

适合：

- 一个请求同时跨多个领域。
- 多轮协调。
- 需要 Supervisor 决定“调用几个 Agent、先后顺序、如何合并”。

当前 LangChain 多智能体指南更推荐这种直接的 **Subagent-as-Tool** supervisor pattern，而不是依赖旧 `langgraph-supervisor` helper package。

# 五、先构建三个独立 Worker Agent

Multi-Agent 的第一原则不是先写 Supervisor，而是先证明每个 Worker 自己能做好一件事。

## 5.1 Record Agent：历史记录查询

这里不接真实医疗系统，使用模拟 Tool。

```python
from langchain.agents import create_agent
from langchain.tools import tool


@tool
def get_history_records(user_id: str) -> str:
    """Return synthetic historical consultation records for a demo user."""
    fake_records = {
        "user_123": [
            "2026-08-10: routine consultation - synthetic demo record",
            "2026-09-02: follow-up - synthetic demo record",
        ]
    }
    return "\n".join(fake_records.get(user_id, ["No synthetic record found."]))


record_agent = create_agent(
    model=build_local_model(),
    tools=[get_history_records],
    system_prompt=(
        "You are the record specialist. "
        "Only summarize synthetic historical records returned by tools. "
        "Do not invent diagnoses."
    ),
)
```

职责边界：

```text
Input:  与历史记录相关的任务
Tools:  get_history_records
Output: 简洁记录摘要
```

## 5.2 Guideline Agent：指南知识

06 不重复完整 RAG 实现。

可以把 02 已经学过的 RAG 思维封装成一个最小工具：

```python
@tool
def search_demo_guideline(query: str) -> str:
    """Search a tiny local synthetic guideline dataset."""
    # 教学版：可以使用本地静态数据或最小 retriever
    ...
```

然后：

```python
guideline_agent = create_agent(
    model=build_local_model(),
    tools=[search_demo_guideline],
    system_prompt=(
        "You are the guideline specialist. "
        "Only summarize retrieved educational guideline text. "
        "Do not provide personal diagnosis or treatment decisions."
    ),
)
```

职责边界：

```text
Input:  指南/知识类任务
Tools:  local guideline search
Output: 基于检索证据的摘要
```

## 5.3 Doctor Agent：医生信息查询

```python
@tool
def find_demo_doctors(specialty: str) -> list[dict]:
    """Return synthetic doctor directory entries."""
    data = {
        "general": [
            {"name": "Dr Demo A", "specialty": "general"},
            {"name": "Dr Demo B", "specialty": "general"},
        ]
    }
    return data.get(specialty, [])


doctor_agent = create_agent(
    model=build_local_model(),
    tools=[find_demo_doctors],
    system_prompt=(
        "You are the directory specialist. "
        "Only report synthetic directory information returned by tools."
    ),
)
```

三个 Worker 应该先分别 E2E：

```text
Record Agent     PASS
Guideline Agent  PASS
Doctor Agent     PASS
```

然后再做 Multi-Agent。

# 六、Pattern A：用 LangGraph 构建 Router Multi-Agent

这是最贴近原 PDF 架构的实现。

## 6.1 State

```python
from typing import Literal
from typing_extensions import TypedDict


class MultiAgentState(TypedDict):
    query: str
    route: str
    worker_result: str
    final_answer: str
```

## 6.2 Router

教学阶段可以先用确定性 Router，这样不把“路由错误”和“模型不稳定”混在一起。

```python
def route_query(state: MultiAgentState):
    query = state["query"].lower()

    if "history" in query or "record" in query:
        route = "record"
    elif "guideline" in query or "guide" in query:
        route = "guideline"
    elif "doctor" in query or "specialist" in query:
        route = "doctor"
    else:
        route = "refuse"

    return {"route": route}
```

真正项目中可以把 Router 换成：

- LLM structured output。
- 规则 + LLM 混合路由。
- 分类模型。

但教学阶段先用 deterministic router，更容易看到 Graph 本身。

## 6.3 Worker Node

```python
def record_node(state: MultiAgentState):
    result = record_agent.invoke({
        "messages": [{"role": "user", "content": state["query"]}]
    })
    return {"worker_result": result["messages"][-1].content}
```

其他 Worker 同理。

## 6.4 Conditional Routing

```python
from langgraph.graph import StateGraph, START, END


def choose_worker(state: MultiAgentState) -> Literal[
    "record", "guideline", "doctor", "refuse"
]:
    return state["route"]


builder = StateGraph(MultiAgentState)
builder.add_node("router", route_query)
builder.add_node("record", record_node)
builder.add_node("guideline", guideline_node)
builder.add_node("doctor", doctor_node)
builder.add_node("refuse", refuse_node)
builder.add_node("aggregate", aggregate_node)

builder.add_edge(START, "router")
builder.add_conditional_edges("router", choose_worker)

for name in ["record", "guideline", "doctor", "refuse"]:
    builder.add_edge(name, "aggregate")

builder.add_edge("aggregate", END)

graph = builder.compile()
```

核心链路：

```text
Query
 ↓
Router
 ↓
One Worker
 ↓
Aggregate
 ↓
Answer
```

这里虽然有多个 Agent，但每次请求通常只选择一个，所以它是 **Router architecture**。

# 七、Pattern B：Supervisor + Subagents-as-Tools（当前更推荐）

如果希望真正做 Supervisor，不要只做一次分类。

Supervisor 自己就是一个 Agent，而 Worker Agent 通过 Tool 暴露给它。

## 7.1 包装 Subagent Tool

```python
from langchain.tools import tool


@tool
def ask_record_agent(task: str) -> str:
    """Delegate synthetic record-history tasks to the record specialist."""
    result = record_agent.invoke({
        "messages": [{"role": "user", "content": task}]
    })
    return result["messages"][-1].content


@tool
def ask_guideline_agent(task: str) -> str:
    """Delegate educational guideline tasks to the guideline specialist."""
    result = guideline_agent.invoke({
        "messages": [{"role": "user", "content": task}]
    })
    return result["messages"][-1].content


@tool
def ask_doctor_agent(task: str) -> str:
    """Delegate synthetic directory tasks to the doctor-directory specialist."""
    result = doctor_agent.invoke({
        "messages": [{"role": "user", "content": task}]
    })
    return result["messages"][-1].content
```

Worker Agent 在这里变成 Supervisor 眼中的高层 Tool：

```text
Supervisor sees:
- ask_record_agent
- ask_guideline_agent
- ask_doctor_agent

Supervisor does NOT see:
- get_history_records
- search_demo_guideline
- find_demo_doctors
```

这就是职责分层。

## 7.2 创建 Supervisor

```python
supervisor = create_agent(
    model=build_local_model(),
    tools=[
        ask_record_agent,
        ask_guideline_agent,
        ask_doctor_agent,
    ],
    system_prompt=(
        "You are the supervisor. "
        "Delegate domain-specific tasks to specialist agents. "
        "Call more than one specialist when the user request spans multiple domains. "
        "Synthesize only the specialists' final results."
    ),
)
```

这才是当前更典型的 supervisor pattern：

```text
User
 ↓
Supervisor LLM
 ↓
Subagent Tool Call(s)
 ↓
Worker Agent(s)
 ↓
Tool Result(s)
 ↓
Supervisor
 ↓
Final Answer
```

# 八、为什么当前推荐 Subagent-as-Tool？

官方当前多智能体指南强调这个模式的几个优势。

## 8.1 Context Isolation

Supervisor 不需要看到 Worker 内部所有 Tool Call 和中间消息。

```text
Supervisor Context
    ↓ task only
Worker Context
    ↓ internal work
Final Summary
    ↓
Supervisor Context
```

相比把全部消息历史广播给所有 Agent：

- 更省 token。
- Worker Prompt 更干净。
- 不容易被无关上下文干扰。
- 每个 Worker 更容易单独测试。

## 8.2 Tool Namespace 更小

如果直接把所有底层 Tool 给 Supervisor：

```text
Supervisor tools:
20 / 30 / 50 tools
```

模型选择工具会越来越难。

多智能体后，Supervisor 只看到高层能力：

```text
record_specialist
guideline_specialist
doctor_specialist
```

底层 Tool 被各 Worker 隔离。

## 8.3 Worker 可以独立演进

例如未来：

```text
Guideline Agent
Local static search
      ↓
Vector Store RAG
      ↓
MCP Search Service
```

Supervisor 的调用接口可以完全不变。

# 九、Subagent 的 Context Engineering

多智能体最难的地方之一不是 Graph，而是：

> **给 Subagent 什么信息？让它返回什么信息？**

当前官方文档把这个问题拆成三类：

```text
1. Subagent specs
2. Subagent inputs
3. Subagent outputs
```

## 9.1 Specs：名字和描述决定 Supervisor 会不会选它

例如：

```python
@tool
def ask_guideline_agent(task: str) -> str:
    """Use for educational guideline lookup and evidence summaries."""
```

如果描述太模糊：

```text
“Useful tool.”
```

Supervisor 很难做正确路由。

所以 Tool Description 本身就是 routing interface。

## 9.2 Input：不要无脑传整个聊天记录

通常 Worker 只需要一个任务：

```text
“查询 user_123 的模拟历史记录并返回三行摘要”
```

而不是：

```text
Supervisor 的全部几十轮聊天历史
+ 其他 Worker 的所有中间消息
+ Tool Calls
+ Debug 输出
```

## 9.3 Output：优先只返回最终结果

Supervisor 最需要的是：

```text
Worker final result
```

而不是 Worker 的全部内部轨迹。

可以把 Worker 当作函数：

```text
Task
 ↓
Subagent
 ↓
Concise Result
```

这也是多智能体降低上下文膨胀的关键。

# 十、并行 Subagent 调用

Supervisor 有时可以一次请求多个专家。

例如用户问：

```text
“给我总结模拟历史记录，同时列出可联系的医生目录。”
```

理想情况：

```text
Supervisor
 ├─ ask_record_agent(...)
 └─ ask_doctor_agent(...)
       ↓ parallel if runtime/model supports
     results
       ↓
  Supervisor synthesis
```

当前 LangChain 多智能体指南明确支持一个 Supervisor 在一轮中调用多个 Subagent；如果模型产生多个 Tool Calls，运行时可以执行并行 Tool Calls。

但要注意：

- 并不是所有本地模型都稳定支持 parallel tool calling。
- Foundry Local 上如果模型只生成一个 Tool Call，也不代表 Multi-Agent 架构失败。
- 教学验证时应把“顺序调用正确”设为核心 PASS，把“并行”设为增强项。

真正需要确定性并行时，可以直接使用 05 学过的 LangGraph fan-out / `Send`，而不是完全依赖 LLM 自主并行。

# 十一、Router vs Supervisor：不要混淆

可以用一句话区分：

```text
Router:
“这个问题交给谁？”

Supervisor:
“这个任务需要哪些专家？怎么拆？先后/并行怎么做？结果怎么合并？”
```

| 维度 | Router | Supervisor |
|---|---|---|
| 控制方式 | 一次分流 | 持续 Agent Loop |
| 会不会多次调用 Worker | 通常不会 | 可以 |
| 会不会一次调用多个 Worker | 一般不做 | 可以 |
| 是否维护主对话上下文 | 可选 | 通常是 |
| 适合场景 | 清晰单领域分类 | 多领域复杂任务 |
| 实现 | StateGraph 条件边 / 分类器 | Agent + Subagents-as-Tools |

所以原 PDF 里的“supervisor 节点”如果只负责一次分类，建议在新版代码里命名为：

```text
router
```

这样概念更准确。

# 十二、结果汇总应该放在哪里？

原 PDF 有一个统一“结果汇总”节点。

这在 Router 架构里非常合理：

```text
Worker Result
    ↓
Aggregate Node
    ↓
Final Answer
```

在 Supervisor 架构中，Supervisor 本身就可以做结果综合：

```text
Subagent Result A
Subagent Result B
      ↓
Supervisor Model
      ↓
Final Answer
```

两种都对。

选择原则：

- **想要确定性格式**：单独 `aggregate` Node。
- **需要跨多个专家自然语言综合**：Supervisor synthesis。
- **高风险业务结果**：最好先结构化结果，再由确定性代码验证，最后再生成自然语言。

# 十三、失败隔离：一个 Worker 失败怎么办？

Multi-Agent 不能假设所有 Worker 永远成功。

例如：

```text
Supervisor
 ├─ Record Agent   PASS
 └─ Doctor Agent   FAIL
```

至少要区分：

```text
Worker execution failed
vs
Worker returned “no data”
```

可以在包装工具层做统一错误转换：

```python
@tool
def ask_doctor_agent(task: str) -> str:
    """Delegate directory lookup to the doctor specialist."""
    try:
        result = doctor_agent.invoke({
            "messages": [{"role": "user", "content": task}]
        })
        return result["messages"][-1].content
    except Exception as exc:
        return f"DOCTOR_AGENT_ERROR: {type(exc).__name__}"
```

教学阶段重点理解：

> Worker 的失败应该被限制在 Worker 边界内，不要让一处错误把所有 Agent 状态搞乱。

更完整的 Retry / Error Handler 在 05 已经学过，可以直接应用到 Worker Node 层。

# 十四、Memory / HITL / Time Travel 为什么留到 07？

原 PDF 在最后留下了几个问题：

- 开发过程如何调试？
- 窗口短期记忆如何处理？
- Human-In-The-Loop 如何集成？
- 如何进行时间回溯？

这些问题仍然成立，而且非常重要。

但 06 的目标应该先收紧：

> **先把多智能体职责划分、路由、协调、上下文边界跑通。**

否则一章同时加入：

```text
Multi-Agent
+ Memory
+ Persistence
+ HITL
+ Time Travel
+ Debugging
```

学习负担会过大。

因此 07 再专门加入这些运行时能力更合理。

# 十五、06 章推荐 Local E2E Stage

后续让 Codex 实现时，建议拆成：

```text
Stage A  三个独立 Worker Agent
Stage B  Deterministic Router baseline
Stage C  Router + LangGraph Worker Nodes
Stage D  统一 Aggregate Node
Stage E  Subagent-as-Tool 封装
Stage F  Supervisor Agent
Stage G  一个请求调用多个 Subagent
Stage H  Context Isolation / Output Filtering
Stage I  Worker Failure Isolation
Stage J  Router vs Supervisor 对比 + Final Verification
```

最关键的两条 E2E：

## Router E2E

```text
User Query
 ↓
Router
 ↓
Correct Worker
 ↓
Worker Tool(s)
 ↓
Aggregate
 ↓
Answer
```

## Supervisor E2E

```text
User
 ↓
Supervisor
 ↓
Subagent Tool Call(s)
 ↓
Worker Agent(s)
 ↓
Worker Tool(s)
 ↓
Subagent Final Result(s)
 ↓
Supervisor
 ↓
Final Answer
```

两条都跑通，才能真正理解：

```text
Router ≠ Supervisor
```

# 十八、章节总结

原课程最重要的思想没有过时：

> **把复杂任务拆给不同 Agent，再统一协调。**

但今天需要把概念进一步分清：

```text
Router
= 一次分类 / 分发

Supervisor
= 持续协调 Subagents 的 Agent

Subagent
= 一个独立专家，拥有自己的 Prompt / Tools / Context

Custom Workflow
= 用 LangGraph 显式控制完整执行图
```

推荐认知链路：

```text
05. LangGraph Core
    ↓
State / Node / Routing / Send / Command
    ↓
06. Multi-Agent
    ↓
Router / Supervisor / Subagent / Context Isolation
    ↓
07. Multi-Agent Workflow
    ↓
Persistence / Streaming / Memory / HITL / Time Travel / Debugging
```

最后记住：

> **多智能体系统真正的难点不是“创建多个 Agent”，而是决定谁负责什么、每个 Agent 看什么、什么时候调用谁、结果怎么返回，以及失败时边界在哪里。**
