# 0. 2026 版最重要的修正

| 原 PDF 中的说法 / 写法 | 现在更准确的理解 |
|---|---|
| Graph 是“有向无环图 DAG” | **错误/过窄。** LangGraph 支持有向图，也支持循环。Agent loop、retry loop、review loop 都依赖循环 |
| LangGraph 是 LangChain 的“子项目” | LangGraph 是独立低层 orchestration framework，可独立于 LangChain 使用；LangChain Agent 构建在 LangGraph runtime 之上 |
| Node 基本是 `state + config` | 当前推荐区分：共享可变数据放 `State`，单次运行的只读依赖/配置放 `context_schema + Runtime` |
| 配置上下文主要放 `configurable` | `RunnableConfig` 仍存在，但应用级 run-scoped context 更推荐 `context_schema` |
| Node 只讲 cache / retry | 当前 `add_node()` 还支持 `error_handler`、`timeout`、`trace_policy` 等策略 |
| Stream 主要 5 种模式 | 当前 `stream()` 核心模式包括 `values / updates / messages / custom / checkpoints / tasks / debug` |
| 子图触发会天然重复 state | 不应该这样理解。Subgraph 的输入/输出取决于共享 schema 或显式转换，不应把“重复”当作正常语义 |
| Graph 最后与 Chain 对比，强调它属于 LangChain | 更准确：LangGraph 是低层状态化编排；LangChain 提供更高层 Agent harness。两者定位不同但紧密集成 |

当前 LangGraph 1.2.12 的定位可以浓缩为：

> **用显式 State + Node + Routing 构建长时间运行、可恢复、可流式、可人工干预的状态化 workflow / agent。**

# 一、Graph 到底是什么？

LangGraph 的 Graph API 本质上是：

```text
State
  ↓
Node A
  ↓
Routing / Edge
  ↓
Node B / Node C / Loop Back
  ↓
State Updates
  ↓
...
```

三个基础元素：

- **State**：整个 workflow 共享的数据结构。
- **Node**：读取当前 State，执行一个步骤，返回 State 的部分更新。
- **Edge / Routing**：决定下一步运行哪个 Node。

## 1.1 最重要的修正：它不是只能做 DAG

原 PDF 把 Graph 描述成 DAG，这会误导你。

LangGraph 可以是：

```text
A → B → C → END
```

也可以是：

```text
        ┌──────────────┐
        ↓              │
START → Agent → Tool ──┘
          ↓
         END
```

后一种就是典型 Agent Loop。

因此更准确的描述是：

> LangGraph 使用有向图表达执行关系，**允许循环**，并通过运行时控制循环次数、状态、持久化与恢复。

## 1.2 最小 Graph

```python
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END


class State(TypedDict):
    text: str


def step_a(state: State):
    return {"text": state["text"] + " -> A"}


def step_b(state: State):
    return {"text": state["text"] + " -> B"}


builder = StateGraph(State)
builder.add_node("step_a", step_a)
builder.add_node("step_b", step_b)
builder.add_edge(START, "step_a")
builder.add_edge("step_a", "step_b")
builder.add_edge("step_b", END)

graph = builder.compile()

print(graph.invoke({"text": "START"}))
# {'text': 'START -> A -> B'}
```

这里要记住：

```text
StateGraph(...)   = Builder
compile()         = 生成可执行 CompiledStateGraph
invoke()/stream() = 真正执行
```

`StateGraph` 本身只是构图器，必须 `compile()` 后才能执行。

# 二、State：Graph 的共享数据模型

State 可以理解为 workflow 的共享 notebook。

每个 Node：

```text
读取 State
   ↓
做自己的工作
   ↓
只返回“需要修改的字段”
   ↓
LangGraph 合并更新
```

当前 `StateGraph` 的核心签名可以理解为：

```text
State -> Partial<State>
```

Node 通常 **不需要返回完整 State**。

## 2.1 TypedDict 是教学阶段最清晰的选择

```python
from typing_extensions import TypedDict


class State(TypedDict):
    query: str
    answer: str
    attempts: int
```

Pydantic / dataclass 等也可以用于 schema，但本章建议优先 `TypedDict`，因为最容易看清 State 更新本质。

## 2.2 Input State / Output State / Overall State

当外部 API 不应该直接看到内部字段时，可以定义不同 schema：

```python
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END


class InputState(TypedDict):
    user_input: str


class OutputState(TypedDict):
    graph_output: str


class OverallState(TypedDict):
    user_input: str
    working_text: str
    graph_output: str


def prepare(state: InputState):
    return {"working_text": state["user_input"].strip()}


def process(state: OverallState):
    return {"graph_output": state["working_text"].upper()}


builder = StateGraph(
    OverallState,
    input_schema=InputState,
    output_schema=OutputState,
)
builder.add_node("prepare", prepare)
builder.add_node("process", process)
builder.add_edge(START, "prepare")
builder.add_edge("prepare", "process")
builder.add_edge("process", END)

graph = builder.compile()
print(graph.invoke({"user_input": "  langgraph  "}))
# {'graph_output': 'LANGGRAPH'}
```

意义：

```text
External Input
     ↓
Input Schema
     ↓
Internal Overall State
     ↓
Output Schema
     ↓
External Output
```

这样内部状态不需要全部暴露给调用者。

# 三、Reducer：State 并不是简单覆盖

如果一个 State key 没有 reducer，新的值通常覆盖旧值。

但很多场景需要：

- 追加消息
- 合并列表
- 聚合并行节点结果

这时使用 reducer。

## 3.1 普通覆盖 vs reducer 聚合

```python
import operator
from typing import Annotated
from typing_extensions import TypedDict


class State(TypedDict):
    values: Annotated[list[int], operator.add]
    status: str
```

如果两个 Node 返回：

```python
{"values": [10], "status": "A"}
{"values": [20], "status": "B"}
```

那么：

```text
values → reducer(add) → [10, 20]
status → 普通覆盖     → "B"（取决于执行/更新语义）
```

并行分支如果会同时写同一个 key，通常必须设计合适的 reducer，否则可能触发 concurrent update 错误。

## 3.2 MessagesState 与 add_messages

对聊天消息，LangGraph 已经提供 `MessagesState`。

```python
from langgraph.graph import MessagesState


def node(state: MessagesState):
    return {
        "messages": [
            {"role": "assistant", "content": "hello"}
        ]
    }
```

它的 `messages` 字段使用消息 reducer，可追加消息，并能根据 message id 更新已有消息。

如果需要自定义 State：

```python
from typing import Annotated
from typing_extensions import TypedDict
from langchain_core.messages import AnyMessage
from langgraph.graph.message import add_messages


class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    task_id: str
```

## 3.3 State 设计原则

优先把 **需要跨 Node 保留的数据** 放 State。

不要把所有东西都塞进去。

特别是：

```text
Prompt 格式化字符串
临时局部变量
可以廉价重新计算的数据
```

一般不需要长期留在 State。

更推荐：

> **State 存 raw data；Node 在需要时再格式化。**

# 四、State vs Runtime Context

这是原 PDF 最需要更新的一部分之一。

现在更推荐明确区分：

| 数据 | 应放哪里 |
|---|---|
| 会在 Node 之间变化 | State |
| 当前 run 的只读上下文，如 user_id / tenant / db client | Context |
| graph 执行控制参数，如 recursion_limit | RunnableConfig |

## 4.1 context_schema + Runtime

```python
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.runtime import Runtime


class State(TypedDict):
    message: str


class Context(TypedDict):
    user_id: str


def greet(state: State, runtime: Runtime[Context]):
    user_id = runtime.context["user_id"]
    return {"message": f"hello {user_id}"}


builder = StateGraph(State, context_schema=Context)
builder.add_node("greet", greet)
builder.add_edge(START, "greet")
builder.add_edge("greet", END)

graph = builder.compile()

print(
    graph.invoke(
        {"message": ""},
        context={"user_id": "user-123"},
    )
)
```

这里：

```text
State.message
→ workflow 中会变化

Context.user_id
→ 这一次 run 的只读上下文
```

原来大量把业务上下文塞进 `config["configurable"]` 的写法，不再是新代码首选。

## 4.2 RunnableConfig 仍然有用

例如：

```python
graph.invoke(
    input_state,
    config={"recursion_limit": 50},
)
```

以后加入 checkpointer 时，`thread_id` 仍通过 configurable config 使用。

所以不是“config 被废弃”，而是职责更清楚：

```text
State   = 可变业务状态
Context = run-scoped 只读业务上下文
Config  = runtime / execution 配置
```

# 五、Node：一个步骤就是一个函数

Node 最常见形式：

```python
def node(state: State):
    return {"field": new_value}
```

也可以使用 Runtime：

```python
def node(state: State, runtime: Runtime[Context]):
    ...
```

Node 的关键原则：

1. 一个 Node 尽量只承担一个清晰步骤。
2. 读取 State / Context。
3. 返回 **Partial State Update**。
4. 不要在没有必要时返回整个 State。

## 5.1 Node 名称

可以显式：

```python
builder.add_node("normalize", normalize)
```

也可以让函数名作为节点名：

```python
builder.add_node(normalize)
```

## 5.2 Cache

LangGraph 支持 Node cache。

```python
import time
from typing_extensions import TypedDict
from langgraph.cache.memory import InMemoryCache
from langgraph.graph import StateGraph, START, END
from langgraph.types import CachePolicy


class State(TypedDict):
    number: int


def expensive_node(state: State):
    time.sleep(1)
    return {"number": state["number"] * 2}


builder = StateGraph(State)
builder.add_node(
    "expensive",
    expensive_node,
    cache_policy=CachePolicy(ttl=30),
)
builder.add_edge(START, "expensive")
builder.add_edge("expensive", END)

graph = builder.compile(cache=InMemoryCache())

print(graph.invoke({"number": 5}))
print(graph.invoke({"number": 5}))  # 可命中 cache
```

重要：默认 cache key 基于 **Node input**。

所以如果 Node 的结果还依赖 State 之外的 Context / 外部环境，要谨慎设计 cache key 或干脆不要缓存。

## 5.3 RetryPolicy

```python
from langgraph.types import RetryPolicy

builder.add_node(
    "remote_call",
    remote_call,
    retry_policy=RetryPolicy(
        max_attempts=3,
        retry_on=ConnectionError,
    ),
)
```

适合：

- 网络抖动
- 临时 rate limit
- 短暂外部依赖失败

不适合：

- 参数永远错误
- 权限错误
- 业务规则失败

## 5.4 Error Handler（1.2 重点能力）

当前可以给 Node 声明 `error_handler`。

```python
from langgraph.errors import NodeError
from langgraph.types import Command


def payment_error_handler(state: State, error: NodeError) -> Command:
    return Command(
        update={"status": f"recovered: {error.error}"},
        goto="finalize",
    )


builder.add_node(
    "payment",
    payment_node,
    retry_policy=RetryPolicy(max_attempts=3),
    error_handler=payment_error_handler,
)
```

思路：

```text
Node fails
   ↓
RetryPolicy
   ↓ retries exhausted
Error Handler
   ↓
compensation / fallback branch
```

## 5.5 Timeout / TracePolicy

当前 `add_node()` 还支持：

```text
timeout
trace_policy
```

这些属于运行时工程能力，本章知道它们存在即可，不需要全部展开。

LangGraph 1.2.12 还增加了 `set_node_defaults()`，可给多个 Node 统一设置 retry/cache/error/timeout 默认策略；学习阶段先掌握 Node 级配置更直观。

# 六、Edge：控制流的连接关系

## 6.1 普通 Edge

```python
builder.add_edge("node_a", "node_b")
```

代表：

```text
node_a 完成
   ↓
node_b
```

LangGraph 内置两个虚拟节点：

```python
START
END
```

推荐新代码直接使用：

```python
builder.add_edge(START, "node_a")
builder.add_edge("node_b", END)
```

`set_entry_point()` / `set_finish_point()` 仍可用，但 `START / END` 更直观，也更方便条件入口。

## 6.2 Conditional Edge

```python
from typing import Literal


def route(state: State) -> Literal["positive", "negative"]:
    if state["number"] >= 0:
        return "positive"
    return "negative"


builder.add_conditional_edges(
    "classify",
    route,
)
```

也可以返回逻辑标签，再映射到 Node：

```python
def route(state: State) -> bool:
    return state["number"] >= 0

builder.add_conditional_edges(
    "classify",
    route,
    {
        True: "positive",
        False: "negative",
    },
)
```

## 6.3 循环路由

这正好证明 LangGraph 不是 DAG-only。

```python
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END


class State(TypedDict):
    count: int


def increment(state: State):
    return {"count": state["count"] + 1}


def should_continue(state: State):
    if state["count"] < 3:
        return "increment"
    return END


builder = StateGraph(State)
builder.add_node("increment", increment)
builder.add_edge(START, "increment")
builder.add_conditional_edges("increment", should_continue)

graph = builder.compile()
print(graph.invoke({"count": 0}))
# {'count': 3}
```

流程：

```text
START
 ↓
increment
 ↓
count < 3 ? ──yes──┐
 ↓ no              │
END        ←────────┘
```

如果循环设计错误，可以使用 `recursion_limit` 控制最大执行步数。

# 七、Send：运行时动态 fan-out

普通 conditional edge 决定“下一步去哪里”。

`Send` 更进一步：

> 在运行时，根据当前数据动态创建多个 Node 调用，并给每个调用不同输入。

典型场景：Map-Reduce。

```python
import operator
from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send


class OverallState(TypedDict):
    subjects: list[str]
    results: Annotated[list[str], operator.add]


class ItemState(TypedDict):
    subject: str


def fan_out(state: OverallState):
    return [
        Send("process_item", {"subject": subject})
        for subject in state["subjects"]
    ]


def process_item(state: ItemState):
    return {"results": [f"processed:{state['subject']}"]}


builder = StateGraph(OverallState)
builder.add_node("process_item", process_item)
builder.add_conditional_edges(START, fan_out)
builder.add_edge("process_item", END)

graph = builder.compile()
print(graph.invoke({"subjects": ["A", "B", "C"], "results": []}))
```

概念图：

```text
              ┌→ process_item(A) ─┐
START → fanout ├→ process_item(B) ─┼→ reducer → END
              └→ process_item(C) ─┘
```

这里 `results` 必须有 reducer 来合并并行结果。

## Send vs 普通 Edge

```text
普通 Edge：图构建时路径基本已知
Send：运行时才知道需要启动多少个任务、每个任务输入是什么
```

# 八、Command：在 Node 内同时更新 State + 路由

普通模式：

```text
Node 返回 State Update
        ↓
Edge 决定下一步
```

`Command` 可以把两件事合在一起：

```text
Node
 ↓
Command(
  update=...,
  goto=...
)
```

示例：

```python
from typing import Literal
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command


class State(TypedDict):
    score: int
    result: str


def decide(state: State) -> Command[Literal["pass_node", "fail_node"]]:
    if state["score"] >= 60:
        return Command(
            update={"result": "pass"},
            goto="pass_node",
        )
    return Command(
        update={"result": "fail"},
        goto="fail_node",
    )


def pass_node(state: State):
    return {}


def fail_node(state: State):
    return {}


builder = StateGraph(State)
builder.add_node("decide", decide)
builder.add_node("pass_node", pass_node)
builder.add_node("fail_node", fail_node)
builder.add_edge(START, "decide")
builder.add_edge("pass_node", END)
builder.add_edge("fail_node", END)

graph = builder.compile()
```

## Command vs Conditional Edge

两种都能路由，但思维不同：

**Conditional Edge**：

```text
业务处理
和
路由规则
分开
```

**Command**：

```text
Node 在得到结果后
同时声明更新 + 下一跳
```

选择原则：

- 想让图结构/路由集中可见：Conditional Edge 更清晰。
- 路由天然属于这个 Node 的结果：Command 很自然。

不要为了“新 API”把所有 Edge 都改成 Command。

# 九、Subgraph：把一个 Graph 当成另一个 Graph 的 Node

Subgraph 适合：

- 复用复杂 workflow
- 隔离不同团队/领域逻辑
- Multi-Agent 中把每个 specialist workflow 作为子图

最简单情况：父图和子图共享一部分 State schema。

```python
from typing import Annotated
import operator
from typing_extensions import TypedDict
from langgraph.graph import StateGraph, START, END


class State(TypedDict):
    log: Annotated[list[str], operator.add]


# ---- Subgraph ----
def sub_step(state: State):
    return {"log": ["subgraph"]}

sub_builder = StateGraph(State)
sub_builder.add_node("sub_step", sub_step)
sub_builder.add_edge(START, "sub_step")
sub_builder.add_edge("sub_step", END)
subgraph = sub_builder.compile()


# ---- Parent graph ----
def parent_step(state: State):
    return {"log": ["parent"]}

parent_builder = StateGraph(State)
parent_builder.add_node("parent_step", parent_step)
parent_builder.add_node("subgraph", subgraph)
parent_builder.add_edge(START, "parent_step")
parent_builder.add_edge("parent_step", "subgraph")
parent_builder.add_edge("subgraph", END)

graph = parent_builder.compile()
print(graph.invoke({"log": []}))
# {'log': ['parent', 'subgraph']}
```

不要把 Subgraph 理解为“框架会额外重复 invoke 一次”。

正确关注点是：

```text
父图给子图什么 State？
子图更新哪些 State？
共享 schema 还是需要转换？
```

如果父子图 State schema 不同，就应该写一个 wrapper Node，明确转换输入和输出。

# 十、Streaming：观察 Graph 每一步怎么运行

Graph 不只支持：

```python
graph.invoke(...)
```

还支持：

```python
graph.stream(...)
await graph.ainvoke(...)
async for ... in graph.astream(...)
```

当前主要 stream modes：

| mode | 含义 |
|---|---|
| `values` | 每个 step 后的完整 State |
| `updates` | 每个 Node / task 返回的局部更新 |
| `messages` | 图中 LLM 调用产生的 token/message + metadata |
| `custom` | Node 主动写出的自定义事件 |
| `checkpoints` | 创建 checkpoint 时输出快照事件 |
| `tasks` | task/node 开始和结束事件，含结果/错误 |
| `debug` | 综合 debug 信息 |

## 10.1 updates

```python
for chunk in graph.stream(
    {"count": 0},
    stream_mode="updates",
):
    print(chunk)
```

教学阶段最推荐先观察 `updates`，因为最容易看到：

```text
哪个 Node
→ 更新了哪些 State
```

## 10.2 custom

```python
from typing_extensions import TypedDict
from langgraph.config import get_stream_writer
from langgraph.graph import StateGraph, START, END


class State(TypedDict):
    value: int


def node(state: State):
    writer = get_stream_writer()
    writer({"progress": "node started"})
    return {"value": state["value"] + 1}


graph = (
    StateGraph(State)
    .add_node("node", node)
    .add_edge(START, "node")
    .add_edge("node", END)
    .compile()
)

for chunk in graph.stream({"value": 1}, stream_mode="custom"):
    print(chunk)
```

适合：

- 进度条
- 工具执行阶段
- 调试状态
- 长任务向 UI 报进度

## 10.3 messages

只有 Node 内真的调用了 Chat Model 时，`messages` 才会产生模型流式消息。

所以没有 LLM 的纯 workflow：

```text
messages stream 为空
```

这是正常的。

## 10.4 1.2 的新 streaming 基础设施

LangGraph 1.2 增强了 typed streaming / `stream_events(version="v3")` 等能力。

# 十一、Graph 可视化

原教程使用：

```python
graph.get_graph().draw_mermaid_png()
```

仍然可以，但 PNG 渲染可能依赖额外环境或外部 renderer。

Local-first 学习更稳的方式是先输出 Mermaid：

```python
print(graph.get_graph().draw_mermaid())
```

得到类似：

```text
START --> step_a
step_a --> step_b
step_b --> END
```

再让 IDE / Markdown Mermaid renderer 显示图。

重点不是“生成漂亮图片”，而是检查：

- Node 是否存在
- Edge 是否正确
- 分支是否符合设计
- 是否无意形成循环

# 十二、05 章最重要的设计方法

真正写 LangGraph，不应该先从 API 开始。

更合理的顺序：

```text
1. 先画业务步骤
      ↓
2. 哪些步骤应该成为 Node
      ↓
3. 哪些数据必须跨步骤保留 → State
      ↓
4. 哪些是只读 run context → Context
      ↓
5. 哪些路径固定 → Edge
      ↓
6. 哪些路径由状态决定 → Conditional Edge / Command
      ↓
7. 哪些任务动态并行 → Send
      ↓
8. 哪一块复杂流程值得复用 → Subgraph
      ↓
9. 最后再加 cache/retry/error/streaming
```

## Node 粒度为什么重要？

Node 太大：

```text
难测试
难观察
失败时重做很多工作
难针对单步骤设置 retry/timeout
```

Node 太碎：

```text
图难读
State 过度膨胀
维护成本增加
```

好的 Node 边界通常对应：

- 一个外部调用
- 一个 LLM decision
- 一个纯计算步骤
- 一个有独立失败模式的动作
- 一个值得单独观察/重试的步骤

# 十三、05 章推荐 Local E2E Stage

本章完全可以 **不依赖 LLM** 完成核心学习。

建议后续 Codex 按下面拆：

```text
Stage A  最小 StateGraph：State / Node / Edge
Stage B  Input / Overall / Output State
Stage C  Reducer + MessagesState
Stage D  Context + Runtime
Stage E  Conditional Edge + Loop
Stage F  Cache + Retry + Error Handler
Stage G  Send 动态 fan-out / reduce
Stage H  Command：update + goto
Stage I  Subgraph
Stage J  Streaming：values / updates / custom / tasks
Stage K  Mermaid + final verification
```

核心 E2E：

```text
Input
 ↓
CompiledStateGraph
 ↓
Node
 ↓
State Update
 ↓
Routing
 ↓
Loop / Branch / Fan-out / Subgraph
 ↓
Output
```

这条链路跑通，05 才算真正理解 Graph。

# 十四、05 章应该能够回答的问题

学完以后，你应该能直接解释：

1. 为什么 LangGraph 不是 DAG-only？
2. `StateGraph` 和 `CompiledStateGraph` 有什么区别？
3. Node 为什么返回 Partial State，而不是完整 State？
4. Reducer 解决什么问题？
5. `MessagesState` 做了什么？
6. State 和 Runtime Context 应该怎么分？
7. Edge 与 Conditional Edge 的区别是什么？
8. `Send` 为什么特别适合 map-reduce / 动态并行？
9. `Command` 和 Conditional Edge 怎么选？
10. Subgraph 是如何组合复杂 workflow 的？
11. `values` 和 `updates` stream 有什么区别？
12. Retry、Cache、Error Handler 应该在哪一层处理？

如果这些能讲清楚，05 就不是“会写几个 API”，而是已经真正建立 **Graph orchestration 思维**。

# 十五、章节总结

05 的核心不是 Agent，也不是 LLM。

它真正教的是：

> **怎样把一个复杂过程拆成有状态、可路由、可循环、可并行、可复用、可观察的执行图。**

完整认知：

```text
State
  ↓
Node
  ↓
Partial Update
  ↓
Reducer
  ↓
Edge / Conditional Edge / Command
  ↓
Send / Loop / Subgraph
  ↓
Streaming / Retry / Cache / Error Handling
```

与前面章节的关系：

```text
03. Agent
→ 学高层 Agent Harness 怎么使用 Tool / Memory / HITL

04. MCP
→ 学 Tool 怎么标准化、跨进程复用

05. LangGraph Core
→ 学如何自己掌控底层 State + Control Flow

06. Multi-Agent
→ 再把 LLM / Agent 节点放进 Graph，构建更复杂系统
```

最重要的一条：

> **LangGraph 的价值不是“把流程画成图”，而是把状态、执行步骤、路由和运行时控制变成显式的一等公民。**
